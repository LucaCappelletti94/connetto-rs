# Implementation roadmap

Open implementation work, in recommended order. Architecture decisions live in `docs/architecture/open-questions.md`, this file tracks what remains to build and why. Prune entries as they land.

## wasm spike first, validation before construction

The wasm client work starts BEFORE the robustness pass, deliberately. The reconnect state machine must be shared across native and wasm (see the constraint below), and its seams are speculative until wasm exists to test them. The disalignment that motivated this ordering is RESOLVED: `ConnettoConnection` was built on two SQLite connections to the same file (captured plus uncaptured sibling), which `sqlite-wasm-rs` cannot express (no multiple connections on any VFS). It now holds ONE connection, with capture suspended around server patch applies and rollbacks (`Session::set_enabled` behind a re-enable drop guard), on native and wasm alike. The `loop_emu` suite (echo prevention, rollback, conflict convergence, refresh) passes unchanged on the unified topology.

The spike's goal is to falsify assumptions, not to ship. First findings, all positive:

- **Unification is possible with zero upstream changes.** `diesel-sqlite-session` already exposes `Session::set_enabled` over `sqlite3session_enable` and pins the contract in its integration tests (a write with tracking disabled is not captured, a write after re-enable is). connetto has exactly two capture bypass sites, `apply_patch` (server patches) and `rollback` (inversion of rejected writes), both behind the `apply` connection. Each becomes a disable window with a re-enable guard on the single connection. The WAL pragma is harmless on a VFS without WAL support (SQLite returns the old journal mode, no error), and single connection mode does not need WAL at all.
- **The client core already compiles for wasm32-unknown-unknown.** `cargo check -p connetto-client --target wasm32-unknown-unknown --no-default-features` passes: diesel (the fork has first class wasm sqlite over `sqlite-wasm-rs`), the session extension, zstd, sqlparser, and subql's typed render all cross compile. The only native coupling was the `native-transport` feature (now default on, off for wasm) and one `tokio::spawn`, now split as `ConnettoClient::with_pump` returning the pump future for the caller to drive (`spawn_local` on wasm) with `start` as the feature gated native convenience.
- **The MaybeSend seam is cut and the browser smoke PASSES.** `connetto_core::traits::MaybeSend` is `Send` on native (supertrait plus blanket impl, so native bounds are unchanged) and vacuous on wasm, where transport futures hold JS values and can never be `Send`. The `Transport` methods and the client's transport riding bounds use it, the dispatch layer included, so the whole typed `live()` surface compiles for wasm32. `examples/wasm-smoke` (standalone workspace) holds a `web_sys` WebSocket transport reusing `connetto_core::codec` framing (the wire tags moved there from the feature gated native transport module), and its dedicated worker test `full_sync_loop_in_a_dedicated_worker` runs green in headless Chrome against the real `connetto-server` and Postgres: connect, subscribe with a server translated query, snapshot, a captured local diesel write pushed and applied, the replication echo applied under capture suspension, and a second push proving the echo was NOT recaptured. This is also the full cdylib link proof for the dependency stack. Run it with the demo stack up: `wasm-pack test --headless --chrome examples/wasm-smoke`.

- **The OPFS leg PASSES: the spike's browser questions are all answered.** `tests/opfs.rs` (`opfs_template_boot_live_query_and_persistence`, dedicated worker, headless Chrome, real server and Postgres) installs the sahpool VFS as default, first-boots the replica by importing the baked template through the VFS utility (`std::fs` is a stub on wasm, so the client gained `connect_existing`, connect with no DDL, and `connect_with_plaintext_template`, which is now deleted by E5), runs the pump under `spawn_local` via `ConnettoClient::with_pump`, drives the typed `live()` verb in the browser, sees a local write flow into the live handle, tears down through the RAII chain with the pump's exit awaited, and reopens the same OPFS file on a fresh connection to prove persistence. Baked templates are gone and first boot now uses DDL.

The spike is complete. Every platform seam is now cut and evidence backed: `MaybeSend` for transport futures, `with_pump` for the driving mode, `connect_existing` plus VFS import for storage boot. Reconnect can be built once on these seams. Next in the browser track: the dioxus-web demo and the Yew adapter.

## Browser topology and the relay (decided)

Decisions from the design discussions, in force for everything below. The original SharedWorker-plus-nested-DB-worker drawing is DEAD: Chrome exposes no `Worker` constructor inside a `SharedWorkerGlobalScope` (hit empirically in headless Chrome 150, a years-old open Chromium bug), and hosting the DB tier in the SharedWorker itself would force the relaxed-idb VFS, which mirrors the whole database in RAM with `synchronous=off`. OPFS sahpool in a dedicated worker stays the storage endgame, so the topology pivoted:

- **Topology: a leader tab owns one dedicated DB worker.** Tabs race a Web Locks election, the winner spawns the dedicated DB worker (the only context kind with OPFS sync access handles), and the worker owns the sahpool replica, the server connection, and the relay hub. Leader failover rides the reconnect machinery (see the robustness pass below).
- **Tab wire: per-tab named `BroadcastChannel`s, no broker.** Independent tabs cannot exchange `MessagePort`s without a SharedWorker or ServiceWorker intermediary, but a uniquely named `BroadcastChannel` reaches across unrelated same-origin contexts with in-order delivery, so each tab gets a private two-party link to the DB worker. This also covers Android Chrome, which has no SharedWorker at all. The rendezvous is ack-based (`ready`, `tab:{wire}`, `attached:{wire}` on a shared hello channel) because a `BroadcastChannel` never buffers for future subscribers. `PortTransport` over a `MessagePort` remains for same-context and iframe embeddings.
- **Tab surface: a relay, not a proxy backend.** The tab runs a completely unmodified `ConnettoClient` over a `Transport` to the worker, with its own disposable memory VFS mirror replica. The worker re-serves the connetto wire protocol: it answers the tab handshake, snapshots from its durable replica, and forwards upstream live patches verbatim (`ClientEvent::LivePatch` carries the compressed payload for exactly this). Zero new diesel machinery, the tab's typed `live()` runs against real local SQLite. Durability is unchanged, the tab mirror is a cache and the worker OPFS replica is the persistent tier. The diesel `Proxy` backend alternative was rejected on the tradeoff table (a new backend surface, `Send` bound risk in `diesel-async`, one round trip per read).
- **Tab writes: batched changesets upward, no interactive cross boundary transactions.** The tab captures its writes with the same session machinery and pushes whole changesets through the relay, which forwards them upstream. Local transactions on the tab mirror stay local and cheap. No tab can starve the worker database.
- **Refresh recall stays in the tab.** The tab holds its own `LiveQuery` and `LiveValue` handles against the mirror, so `changed()` firing, re-render, and drop-unsubscribe are the ordinary client machinery with no serialization boundary in the middle. Dead tab cleanup uses `navigator.locks` liveness (each tab holds a lock named after its client id BEFORE connecting, the worker probes it at handshake with `ifAvailable` so lock-less tabs opt out, and the lock coming free reaps the tab), since neither ports nor broadcast channels have a reliable close event.

**Relay increments 1 through 3 are DONE** (`examples/wasm-smoke`, proven in headless Chrome against the real server and Postgres). Increment 1 and 2, in `src/relay.rs`, `src/port.rs`, `tests/relay.rs`: generic snapshots via a throwaway capture session diffing each subscribed table against an empty twin in an attached blank database (`Session::diff`, the twin built by replaying the table's stored DDL with a schema qualifier spliced in), per-table live patch routing from parsed patchsets, and tab writes applied to the worker replica with capture ACTIVE under an abort-on-conflict policy, re-uploaded by the worker connection, with upstream rejections mapped back to the owning tab's sequence number. Increment 3, in `src/relay.rs` (hub), `src/broadcast.rs`, `src/locks.rs`, `src/workers.rs`, `db-worker.js`, `tests/topology.rs`: `relay_session` grew into `RelayHub`, a single-task core fed by channels with one shovel task per tab, so any number of tabs share one worker connection and a tab-level protocol violation closes that tab alone. The topology test runs the real leader shape end to end: the page wins the leader lock, spawns the DB worker (sahpool replica on OPFS, resumed from its persisted cursor when one exists), two tab clients connect over their own broadcast wire channels, a pre-existing row arrives only via snapshot, an external write fans out to both tabs, a tab write lands in Postgres and echoes to the sibling, releasing a tab's liveness lock reaps exactly that tab, and the survivor keeps receiving patches.

Harness facts worth keeping: the wasm-bindgen test runner serves the crate directory, exposes the glue at the stable name `wasm-bindgen-test.js` (generated without a default module path, so worker bootstraps pass `module_or_path` explicitly), and monkey-patches the worker constructors with a console shim that wraps every script in a fresh blob URL, which is why the bootstraps read their query parameters from `import.meta.url` and never from `self.location`.

Relay parity with the direct server is COMPLETE (`docs/plan-relay-parity.md`, Phases 0 through 7, all proven in headless Chrome against the real server and Postgres): aggregate subscriptions multiplexed per tab, full-resync fan-out, the conflict-versus-reject distinction, scoped non-fatal errors, per-tab delivery-credit flow control, handshake-ack schema-version forwarding, and server-gated schema-version staleness detection. A tab behind the relay cannot distinguish it from a direct socket in any frame the client acts on. Next in the browser track: the dioxus-web demo and the Yew adapter.

## Multi-page leader election (DONE)

**Multi-page leader election is DONE** (`examples/wasm-smoke/src/leader.rs`, proven in `tests/election.rs` in headless Chrome against the real server and Postgres). Every page calls `leader::join` with one shared leader lock name, and Web Locks serializes the requests across all same-origin contexts, so exactly one page holds the lock at a time and owns the dedicated DB worker. Handover is the browser's own liveness, not a heartbeat: a leader's context death releases the lock and terminates its child worker, the next queued request is granted, and that new leader spawns a replacement worker that resumes the OPFS replica from its persisted cursor. Tabs converge through the reconnect machinery, so leadership handover reuses the failover path already proven. `Membership::is_leader` reports the role for app UI, and dropping a `Membership` resigns (terminating the worker and releasing the lock), which lets tests model context death deterministically. The election test races two candidates in one page, drops the leader, and watches the survivor promote, spawn a worker, and serve the tab a row written while no worker existed. `topology.rs` now elects through the same helper instead of a hand-rolled leader lock.

A named limit stays open: dropping a `Membership` that has not yet won leadership leaves its queued lock request pending until context death, because the browser only cancels a not-yet-granted request when the context dies. Real pages resign by dying, where this is a non-issue.

## Robustness pass (DONE, with named limits)

**Client reconnect is DONE.** One shared state machine drives native and wasm alike. The seams live in `connetto-client/src/reconnect.rs`: a `TransportFactory` (implemented by any `FnMut` closure returning a connect future), a `Sleeper` (`TokioSleeper` on native, a `setTimeout` wrapper on wasm), and a data-only `ReconnectPolicy` (doubling backoff between a floor and a ceiling, optional attempt budget). No tokio types appear in any signature and the futures are `MaybeSend` bound. `ConnettoClient::with_reconnect` wires it into the pump: a transport-classified failure (only `ClientError::Transport` or a clean close, local faults stay terminal) flips the pump into recovery, which sleeps and reconnects WITHOUT the state lock, resumes via `ConnettoConnection::resume` (re-handshake carrying the highest applied cursor, all local state kept), re-declares every registered subscription from the specs the registry now stores, and emits `ClientEvent::Reconnecting` per attempt plus `ClientEvent::Reconnected` on success. The server then replays retained changes as ordinary live patches or orders a full resync. Proven by `connetto-client/tests/reconnect_live.rs` against the real session manager over loopback with a deterministic offline gate: a live query receives a row missed during the outage with exactly one snapshot ever running, and a write captured while offline re-flushes after the resume (the forced dirty flag) and lands in the server's write target.

**Cursor persistence is DONE and transactional.** Every applied live patch records its cursor into the replica-local `_connetto_meta` table inside the same SQLite transaction as the patch apply, so a crash never separates a row change from its resume point. Snapshot-end cursors persist too, and an empty cursor never regresses a real one (in memory or on disk). `connect_existing` loads the persisted cursor automatically when the caller passes none, which makes any persisted replica (a file, an OPFS import) resume by construction. Proven by the restart test: a reopened file replica answers offline instantly and catches up from the oplog with zero snapshots.

**Leader failover is DONE in its single-leader form** (`examples/wasm-smoke/tests/failover.rs`, headless Chrome, real server and Postgres). The DB worker holds an alive web lock for its whole life and tab transports watch it (`BroadcastTransport::with_peer_liveness`), because a broadcast peer dies silently. Terminating the worker mid-session releases the lock, the tab's transport injects a clean close, and the tab's reconnect driver hunts through `tab_wire_factory` (ready handshake, fresh wire channel per attempt). The replacement worker, spawned by the still-leading page, finds the OPFS replica, resumes it from the persisted cursor, catches up from the oplog, and serves the reconnecting tab a row that was written while NO worker existed. The hub itself also carries upstream reconnect wiring (`RelayHub::with_reconnect` over the same factory and sleeper seams) so a dropped server connection resumes in place while tabs stay attached. What remains for the topology: the multi-page election helper (a real second page racing the leader lock), which is demo-app glue over the seams that now exist.

**Snapshot failure no longer kills the session (DONE).** A `SnapshotSource` failure in `subscribe_row` now rolls the registration back and surfaces as a `NonFatalError` scoped to the one subscription, with the session and its sibling subscriptions alive (`connetto-server/tests/snapshot_nonfatal.rs` pins the frame sequence and the surviving pong). Transport and oplog failures stay fatal.

**Mutation uploads are exactly-once (DONE).** The protocol grew the missing acknowledgement leg: the server confirms every durable apply with `MutationApplied`, deduplicates replays with a durable per-client watermark stored in the write target's own database (`_connetto_mutations`, keyed by user id and client id, advanced in the SAME transaction as the apply, `GREATEST`-monotonic), and reports the watermark in `HandshakeAck.last_applied_seq`. The client persists every pushed mutation in the replica-local `_connetto_pending` table BEFORE the frames leave and resets capture at the same point, making the pending table the single owner of an un-acked mutation, then retires records on the ack, on a reject or conflict rollback, and at handshake for everything at or below the watermark, replaying the rest in order. Replays survive process restarts because the records live in the replica. The hub tier mirrors the scheme for tabs: a per-tab watermark in the ATTACHED hub meta schema (capture-exempt by construction) advances in the same transaction as the replica apply, replayed tab sequences are re-acknowledged without re-applying, and the tab's own pending record retires only when the SERVER ack maps back through the hub. Proven by `connetto-client/tests/mutation_replay.rs` with deterministic stand-ins: a black hole (sent but never processed) forces a replay that applies exactly once, a man-in-the-middle that drops the ack after a real apply proves the watermark retires without a second apply, and a full process restart replays from the persisted record. This also resolved the deferred awaitable-mutation-confirmation item: `ClientEvent::MutationApplied` on the events stream is the server verdict.

Named limits, deliberately open:

- **A write committed locally but never pushed is lost with the process.** The capture session is memory-only between the commit and the next flush, so a crash inside that window (typically one pump step) drops the upload while keeping the local row. Closing it means extracting changesets at commit time into the pending table, a different capture pipeline. The hub tier has the process-local sibling window between its replica apply and the worker's push persist.
- **Evicting past `PENDING_CAP` gives up a replay.** The cap (256 un-acked mutations) is a safety valve against a server that never acknowledges.
- **Retiring at handshake is silent.** Pending mutations the watermark retires on resume do not synthesize `ClientEvent::MutationApplied`, so a flow awaiting a verdict across a reconnect should also watch `Reconnected`.
- **Registering a new live query during an outage fails fast** instead of queueing until the resume. The registered queries all survive and resume.
- **A stale but non-empty snapshot cursor can still regress the resume point** (cursors are opaque to the client, so it cannot compare). Harmless with the in-memory sources (a regressed cursor only widens catchup or forces a resync), but snapshot sources SHOULD return the real watermark of their read.
- **The hub's upstream reconnect is exercised only indirectly** (its resume and re-subscribe path is the same machinery the native tests pin). A browser test would have to kill the shared demo server mid-run.

## Local-only tables

Core BUILT (client tier machinery, templates, tests) and hub fan-out BUILT (multi-tab notes sharing through the DB worker). Full contract in `docs/upstream-synql-tier-generation-contract.md`, decided entries in `docs/architecture/open-questions.md` section 10. Tier is document membership (two Postgres-dialect source files, bare table names, no schema prefix), placement is a second attached SQLite file, and writability is enforced physically.

- Two source documents, one per tier (`schema.sql` and `frontend.sql` in the demo, each baked to its own template by `build.rs`). Cross-document references are generation-time hard errors, live: pg2sqlite validates reference closure per document (default on since PR #46), so a `REFERENCES` crossing the boundary fails the bake, pinned by `cross_tier_reference_fails_the_template_bake`. The duplicate-name check belongs to synql, still pending.
- `ConnettoConnection::attach_local_tier(path)` attaches an existing frontend file (attach-create disabled around the attach, so a missing file fails loudly), `attach_local_tier_ddl(path, ddl)` creates it and applies the schema when the attached database is empty, with `":memory:"` giving the ephemeral tier a `:memory:` replica wants (tabs, tests). Since phase E2 that DDL flavor is also the only way to first-boot a durable tier under an encrypted replica, because the page codec gives an attached database main's key salt: see the encryption section below. The capture session stays on `main`, so local-only tables are physically incapable of uploading: a note write produces no `MutationHeader` (`push` returns `None`) and the destroy-on-reject hazard is gone by placement. Pinned by `crates/connetto-client/tests/local_tier.rs` and the browser test `examples/wasm-smoke/tests/local_tier.rs`.
- Live queries dispatch by a runtime lookup of the attached tier's catalog (`local_tables`): local rows skip the server subscription and refresh from local writes, local aggregates re-execute locally through the wire decoder (`json_quote` probe, bootstrap answered immediately), mixed rows auto-subscribe each synced table whole for the handle's lifetime (`SELECT * FROM "t"`, dropped with the handle), mixed aggregates hard-error at registration. All pinned by the tier test suites.
- Read-only synced tables are the other enforcement mechanism, kept distinct: pg2sqlite role translation, where the RLS branch already denies via a view without `INSTEAD OF` triggers and the non-RLS branch gains `RAISE(ABORT)` deny triggers (landed in the pinned pg2sqlite), with authoritative applies running in a triggers-disabled window. The server catalog stays as the version skew backstop.
- No cfg features in the generated crates: documents map to modules, the server consumes only the shared document, and the old deferred cell (visible-but-never-replicated tables for live aggregates) dissolves because local aggregates now have a home.
- Hub fan-out for local tables is BUILT (`examples/wasm-smoke/src/relay.rs`, pinned by `tests/notes_fanout.rs` in headless Chrome). The DB worker first-boots the frontend tier from DDL and the hub serves it through a `LocalTier`: a second connection whose main schema IS the tier file, because `sqlite3changeset_apply` only ever targets `main`. Tab mirrors hold both tiers in their main schema (`DEMO_TAB_DDL`) and the HUB keeps the tiers apart: a tab mutation is classified by the tables its changeset touches, a pure local one commits into the tier database together with a per-tab watermark (`_connetto_tab_mutations`, advanced in the same transaction, mirroring the server's `_connetto_mutations` design), is acknowledged by the hub itself as the tier's terminal authority, and is fanned out to the other tabs as a patchset. A mixed changeset is rejected as non-fatal rather than split.

## Replica retention and eviction

The replica holds the union of subscribed query results, so bloat control decomposes into rotating time-windowed subscriptions (a standing `WHERE created_at > X` fixes `X` at registration, rotation means periodic re-subscribe with a fresh bound) and local eviction of rows no active subscription covers. Eviction MUST run with capture suspended (the same `SuspendedCapture` window server patches use): through live capture it would be recorded and sync to the backend as real deletes. Interplay with resume cursors and per table retention declared in the synql schema needs its own design doc before any code.

Physical file trimming belongs to the same design doc. Eviction alone leaves free pages, so the templates should bake `PRAGMA auto_vacuum = INCREMENTAL` (it must be set before the first table exists) and the client should run periodic `PRAGMA incremental_vacuum` plus `PRAGMA wal_checkpoint(TRUNCATE)` for WAL growth. For at-rest size, standard SQLite has no native page compression (ZIPVFS and CEROD are proprietary), and transparent column compression is ruled out after evaluation: `sqlite-zstd` is unusable here (it binds `rusqlite`, a second `libsqlite3-sys` pin against diesel's, and has no `wasm32-unknown-unknown` build at all), and a homegrown replacement would still be the same rename-view-triggers rewrite, which can never cover synced tables because `sqlite3changeset_apply` cannot deliver into a view (every row misfires as a per-row `Constraint` conflict that a server-wins policy omits, pinned by `crates/connetto-client/tests/rls_name_mapping.rs`) while changeset old-image comparisons would misfire against compressed bytes on every server UPDATE or DELETE. A frontend-only size win does not justify a runtime crate plus a pg2sqlite transform. If one frontend column ever genuinely bloats, the proportionate tool is explicit compression: the app calls `zstd` (already a workspace dependency, already exercised in the browser tests) and stores a BLOB. The frontend database bloats only with app-created data, so its tools are app deletion policy, vacuum, and explicit compressed columns, never sync-side eviction.

## wasm client, after the spike

De-risked so far: `sqlite-wasm-rs` compiles and links SQLite 3.53 with `SQLITE_ENABLE_SESSION` and `SQLITE_ENABLE_PREUPDATE_HOOK` for `wasm32-unknown-unknown` with the stock toolchain, and the spike's template-based first boot (`connect_with_plaintext_template`, now deleted by E5) mapped directly onto OPFS as fetch bytes, write file, no DDL execution. The spike, the relay increments, the robustness pass, and the multi-page election above settle the topology, the transports, the driving mode, reconnect, and leadership.

The dioxus-web demo (`examples/dioxus-web-demo`) is VERIFIED end to end in a real browser (headless Chromium via `dx serve`, against `connetto-server` on 7777 and the long-lived `connetto-demo-pg`). Proven: a single window reaches `connected` and both panes render, "Add order" and "Save note" both write, two windows of one device converge on `orders` through the full Postgres CDC round trip and on `notes` through the DB worker hub without ever reaching the server, the tier boundary holds (new order ids land in Postgres `orders` while no `notes` table exists server side), and leader failover works (closing the leader lets a follower win the Web Locks election, spawn a replacement worker that resumes the OPFS replica from its persisted cursor, and keep serving, with a post-failover write round-tripping to Postgres).

Graceful degradation when OPFS is unavailable is also verified: `boot_db_worker` (`crates/connetto-web/src/workers.rs`) tries the sahpool OPFS VFS and, when the browser refuses it (a Firefox private window rejects `navigator.storage.getDirectory` with a `SecurityError`), falls back to the in-memory VFS that `sqlite-wasm-rs` already registers as the default at init. The worker still boots and serves the full topology for the session, trading away persistence and cross-window OPFS sharing. Proven in headless Chromium by forcing `getDirectory` to throw inside the real worker: sahpool calls it once, is rejected, and the worker still reaches `serving` with the tab `connected` and both `orders` (synced) and `notes` (device-local) writes applying.

The Yew adapter is DONE and verified. `connetto-yew` (`crates/connetto-yew`) is a root workspace member mirroring `connetto-dioxus`: one `use_live` hook dispatching at compile time through `Watchable`/`LiveHandle` so a row query yields state of `Vec<R>` and a scalar aggregate state of `Option<V>`. Yew's `spawn_local` is detached (unlike a dioxus scope task), so the hook wraps its driver in a `futures_util` `Abortable` and aborts it from the effect cleanup, preserving the drop-unsubscribe contract on unmount. The `examples/yew-web-demo` (built by trunk, served over the same `connetto-server` and `connetto-demo-pg`) is VERIFIED end to end in headless Chromium: a window reaches `connected`, "Add order" and "Save note" both write, two windows converge on `orders` through the full Postgres CDC round trip (client 380 matches Postgres 380) and on `notes` through the DB worker hub with no `notes` table server side. The remaining browser-track work is the smaller deferred items below.

Worker bootstrap is owned by `connetto-web` and NEITHER demo ships a JS worker file. `spawn_db_worker` (`crates/connetto-web/src/workers.rs`) takes a `WorkerBootstrap` selecting how the app's glue initializes: `Glue` points the `Worker` straight at a self-initializing glue (dx appends an auto-init shim, so importing it instantiates the wasm and runs `main`). `Generated` builds a blob module that imports the glue and calls `init` with the wasm URL derived from the glue (for a stock wasm-bindgen glue such as trunk's, whose built-in default would fetch the un-hashed name). `Script(url)` keeps the older external-bootstrap path (a file that reads the glue from a `glue` query), still used by the `wasm-smoke` suite. In every mode the worker runs `main`, which boots the DB tier in its no-`Window` branch. The dioxus demo passes `Glue`, the Yew demo passes `Generated`, so both ship zero worker JS.

## Smaller deferred items

- `watch_fn(|| build_query())` closure variant for boxed and dynamic queries, which cannot carry the compile time dispatch markers. Done: `connetto-client` adds `ConnettoClient::watch_fn`, a row live query that sources each query instance from a `Fn() -> Q` factory instead of cloning a stored value, so a boxed (`.into_boxed()`) or otherwise dynamic query that is neither `Clone` nor marked can go live in `live.rs`. `watch` is now a thin delegation (`watch_fn(move || query.clone())`), leaving one row-watch implementation, and the factory is rendered once, run once for the offline-first initial load, then re-run per refresh, so it must build an equivalent query each call. The value path stays `watch_value_with` (a boxed aggregate renders once and never re-runs, so no factory buys anything). Proven in `tests/loop_emu.rs`: a boxed row query built by a closure goes live and refreshes on a CDC patch, it collapses onto one wire subscription with an equivalent typed `live()` watch, and an aggregate shape is rejected on the row path.
- `use_live_fn` adapter hooks wrapping `watch_fn` for boxed and dynamic row queries in components. Done: `connetto-dioxus` and `connetto-yew` each add `use_live_fn(client, build)` beside `use_live`, taking a query-builder closure and yielding the same `UseLive<Vec<R>>` for a boxed (`.into_boxed()`) or otherwise dynamic row query. Each mirrors its adapter's existing driver-cancellation contract (dioxus scope task drop, yew `Abortable` abort on unmount), so drop-unsubscribe still composes with the component lifecycle. The dioxus hook is proven by a `VirtualDom` test in `tests/hook.rs` (a boxed row query bootstraps from a seed row and follows a CDC insert), the yew hook compiles against the same bounds and rides the browser demo for its runtime proof, as the adapter has no headless vdom.
- Subscription dedup by SQL hash, so identical queries from many components share one server subscription. Done: `connetto-client` collapses identical `(query, binds)` specs onto one ref-counted wire subscription in `live.rs`, with aggregate fan-out and late-joiner bootstrap caching, proven in `tests/loop_emu.rs`.
- `LiveValue` decode support for custom user-declared aggregates beyond the built-in family. Done: `connetto-client`'s `AggregateWire` family now spans the standard diesel SQL types a custom aggregate returns (`Bool`, the temporal types, `Binary`, `Json` and `Jsonb`, and the non-nullable numeric and text variants), with `Uuid` and `Timestamptz` behind the opt-in `postgres-types` feature since the orphan rule bars a downstream crate from mapping diesel's own types. The wire-lenient primitives are public as `dsl::wire` so an application maps its own SQL type by implementing `AggregateWire` for it, and `watch_value_with` exposes the decoder-parameterized runtime path for boxed or dynamic value queries. The typed `live()` path classifies a custom aggregate from diesel's `IsAggregate` marker rather than the fixed function-name list, so the name-based SQL classification (the relay and untyped runtime paths) stays scoped to the built-in family on purpose. Pinned by `crates/connetto-server`'s `wire_contract` test (the exact `value_to_json` bytes), `connetto-client`'s decode unit tests, a temporal aggregate in `tests/loop_emu.rs`, and a custom-aggregate extension-seam case in `tests/local_tier.rs`.
- The demo id scheme (pid banded integers) stood in for a real distributed key strategy. Done: every app's synced `orders` table now authors client-generated UUID v7 blob keys through a column `DEFAULT (uuidv7())`, where pg2sqlite bakes `DEFAULT gen_random_uuid()` to `id BLOB PRIMARY KEY DEFAULT (uuidv7()) CHECK (length(id) = 16) NOT NULL` under `with_uuid_representation(Blob).with_uuid_function_name("uuidv7")`, and connetto mints the key on each connection it opens. connetto exposes a generic custom-SQL-function registrar, `SqlFunctions` on `ClientConfig` and `DbWorkerConfig` (`connetto-client/src/lib.rs`), applied right after `establish` at every connection seam, with no built-in functions: each app registers its own `uuidv7` (native `Uuid::now_v7`, wasm hand-built from `Date::now` plus `Math::random`), so an offline client authors a synced-table key with no server round trip and no coordination. Local-only tables (the demos' `notes`) stay integer by design, since a device-private single-writer table has no distributed-key requirement and integer keys keep the suite free of same-millisecond ordering concerns.
- The `SqlFunctions` registrar plus pg2sqlite's representation options (`with_uuid_representation`, `with_uuid_function_name`, and the wider representation surface) is the established pattern for supporting further non-obvious SQLite data types across all apps: declare the diesel function, bake the matching column `DEFAULT` or codec, and register the implementation on every replica connection connetto opens.
- Document and configure the SQLite hardening surface on replica connections (defensive mode, `set_attach_create_enabled`, `set_attach_write_enabled`, limits). The knobs exist in the pinned diesel fork and the upstream proposal is open as `diesel-rs/diesel#5128`. A vague security guarantee on its own, so it is a deliberate documentation and configuration pass, not enforcement.

## Authentication (phases 1 to 6 landed)

The authentication architecture is decided and written up in `docs/architecture/11-authentication.md`. connetto uses Backend-For-Frontend: connetto-server is the OAuth client, verifies the provider token once at login through a per-provider registry, maps the claims to a `user_id`, and mints its own signed access token plus a stored rotating refresh token. Identity, sessions, and retained provider tokens live in one auth store with two variants, an in-memory store (single-server, ephemeral) and a database store (durable, mesh-capable). The handshake verifies connetto's own token locally and checks session liveness, building the `AuthContext` that RLS already consumes and closing the current hole where `run_handshake` trusts the client-supplied id. The phased build plan, the resolved open questions (section 11 of `open-questions.md`), and the verified dependency choices (`oauth2` 5.0.0, `openidconnect` 4.0.1, both wasm-clean, no fork needed) live in that chapter.

Phase 1 (core seams) is landed and green. `connetto-core` gained the `SessionVerifier` trait plus `SessionVerifyError`, the `TrustingSessionVerifier` stand-in, and the `FatalErrorReason::AuthenticationFailed` wire reason (the unused `AuthTokenInvalid` variant was renamed to it, so the enum carries one credential-rejection reason rather than two). `run_handshake` now resolves identity through a runtime `Arc<dyn SessionVerifier>` field on `SessionManager` (default `TrustingSessionVerifier`, injectable through `with_session_verifier`) over `Handshake.auth_token`, and on refusal sends `AuthenticationFailed` and terminates before any subscription or catchup work. Identity is the verified token, never the client-supplied `client_id`, so a deployment that injects a real verifier closes the spoofing hole. Proven by `crates/connetto-server/tests/authentication.rs` (absent and forged credentials refused, a verified identity ignores a spoofed `client_id`). The client binary and the RLS tests now carry identity in the token.

Phase 2 (session authority and the auth store) is landed and green in `connetto-server::authn`. connetto mints and verifies its own access token with `jsonwebtoken` (Ed25519, ring-backed, native backend only): `TokenAuthority` pins the algorithm (so `none` and any other algorithm are refused), the issuer, the audience, and the expiry, and rebuilds the `AuthContext` from the signature. The `AuthStore` trait holds the identity mapping, the sessions, and the rotating refresh tokens, with two variants: `InMemoryAuthStore` (deterministic UUID v5 identity, single-server, ephemeral) and `DbAuthStore` (linking table through typed diesel, durable, mesh-capable, behind `pg-async`). The refresh token is `"<session_id>.<secret>"` with only the SHA-256 stored, rotates on every use, and a rotated-out token presented for a live session is theft that revokes the session. `AuthService::login` and `refresh` mint and rotate over the store, `ConnettoSessionVerifier` is the real `SessionVerifier` (verify token, then check store liveness), and the login and refresh HTTP endpoints are served with `axum`. Lifetimes are `AuthConfig` (short access token, sliding refresh window under an absolute ceiling, conservative overridable defaults). The server binary wires it behind `CONNETTO_AUTH` (`in-memory` or `database`), serving `/auth/login` and `/auth/refresh` on `CONNETTO_AUTH_BIND` and injecting the real verifier, while the default stays trusting for dev and the pre-acquisition client loops. Proven Docker-free by `tests/authn_flow.rs` (login token opens a handshake, revocation refuses it, refresh rotates and reuse is theft, an expired or wrong-key token is refused, HTTP login and refresh roundtrip). The database store is pinned by the Docker-gated `tests/authn_db.rs`.

Phase 3 (provider verification and token retention) is landed and green in `connetto-server::authn`. The `IdentityProvider` trait plus a runtime `ProviderRegistry` (indexed by issuer, with a matcher fallback for any-tenant Microsoft and a by-name lookup to start a flow) drive the Authorization Code plus PKCE flow over `openidconnect` 4 (pure-Rust crypto, `reqwest` transport, native only). `GenericOidcProvider` discovers metadata and JWKS, builds a fixed-typestate `CoreClient`, and verifies the ID token (signature, issuer, audience, expiry, nonce) mapping `(iss, sub)` plus email and tenant to a `ResolvedIdentity`, and the `google` and `microsoft` presets configure it (Microsoft accepts the `.../v2.0` any-tenant issuer via `require_issuer_match(false)` plus its own matcher). `AssuranceRequirement` sends `acr_values` and `max_age` on the authorize request and enforces the `acr` allowlist and required `amr` on the verified token, so forcing MFA is a config setting. `PermissiveProvider` is the stand-in that verifies nothing for tests and local loops. Retained provider tokens live in the store (`connetto_provider_tokens` table for the database variant) and `AuthService::provider_access_token` is the lazy refreshing accessor: it refreshes inline against the provider when the stored token is about to expire, persists the rotation, serializes concurrent callers per session on one node, and never emits a provider token to a client (server-side only, preserving BFF). The HTTP layer now serves `GET /auth/login?provider=` (redirect, `PendingLogins` holds the PKCE verifier and nonce keyed by `state`) and `GET /auth/callback` (exchange, verify, mint connetto tokens), with the server binary registering a provider from `CONNETTO_OIDC_PROVIDER` (`google`/`microsoft`/`generic`, else a permissive dev provider). Proven Docker-free by `tests/provider.rs` (a locally minted, locally signed ID token verifies and maps, a wrong nonce or audience is refused, MFA `amr` is enforced, the accessor refreshes an expired token and leaves a valid one) plus unit tests for registry routing and the Microsoft issuer matcher, and Docker-gated by the retained-token half of `tests/authn_db.rs`.

Phase 4 (native client acquisition) is landed and green. connetto-server now doubles as an authorization server to its own loopback clients: `GET /auth/login` accepts a client `redirect_uri`, `code_challenge` (the client's own PKCE S256), and `state`. The provider callback mints a one-time connetto authorization code (held in `AuthCodes`, bound to the challenge) and redirects the browser back to the loopback, and `POST /auth/token` redeems that code once, verifying the PKCE verifier, for the token pair. On the client, `connetto-client`'s `native-auth` feature adds `NativeAuthenticator`: it generates PKCE, binds a `127.0.0.1` listener, opens the system browser (`open` 5.4, `that_detached`) at the login endpoint, catches the redirected code on the loopback, exchanges it, and stores the rotating refresh token in OS secure storage (`keyring` 3.6: Keychain, Credential Manager, daemon-free Linux keyutils) behind a `RefreshTokenStore` trait (`KeyringStore` real, `MemoryRefreshStore` for tests). The browser opener is injectable. `acquire` silently refreshes when a refresh token is stored and only logs in interactively otherwise, and `ConnettoConnection::with_token_source` takes the authenticator's refresh-only `AccessTokenSource` so a reconnect resume refreshes the access token with no user interaction (no `ClientConfig` churn: the source lives on the connection, consulted at resume, first connect uses `auth_token`). Proven Docker-free by `connetto-server/tests/authn_flow.rs::loopback_code_exchange_with_pkce` (start redirect carries state, callback redirects with a one-time code, exchange succeeds, a reused code and a wrong verifier are both `400`) and `connetto-client/tests/native_auth.rs` (a fake browser walks the provider round-trip, the authenticator's loopback catches the code, exchanges it, stores and rotates the refresh token, the token source refreshes, and a second authenticator silently reacquires without opening the browser).

Phase 5 (browser client acquisition) is landed in `connetto-web`, verified by a wasm32 build plus clippy in that standalone workspace (its end-to-end proof is a headless-Chrome run, offered separately). The dedicated DB worker owns token custody: `BrowserAuthenticator` mints the PKCE verifier and, in `boot_db_worker` when a `WorkerAuthConfig` is set, either silently refreshes from the OPFS-stored refresh token (a cold start or a leader failover resumes with no interaction) or produces a login URL. `RefreshStore` persists the rotating refresh token worker-only in an OPFS-backed SQLite table (the same sahpool VFS the replica uses, degrading to in-memory when OPFS is unavailable). The worker posts to connetto-server's `/auth/token` and `/auth/refresh` through `web-sys` `fetch` (getrandom js entropy, sha2 plus base64 for the S256 challenge). Interactive login runs over a `connetto-login` `BroadcastChannel`: the worker broadcasts `LoginMessage::Request { url }`, a tab navigates and its callback route calls `deliver_login_code`, which posts `LoginMessage::Code { code, state }` back, and the worker exchanges it. The enforced invariant is structural: `LoginMessage` has no variant that can carry a token, so the worker's custody is a real boundary and no worker message ever emits a token to a tab. `DbWorkerConfig` gained `auth: Option<WorkerAuthConfig>` and `auth_db_name` (the demos pass `None`, unchanged behavior).

Phase 6 (offline and teardown) is landed and green, closing the plan. Re-auth on reconnect is now terminal-aware: `exchange_handshake` maps a `FatalError(AuthenticationFailed)` to `ClientError::Auth`, and the reconnect driver's `recover` returns a three-way `Recovery` so an auth-fatal resume (a rejected credential, or a silent refresh whose refresh token is gone) stops the backoff loop and the pump emits the new terminal `ClientEvent::AuthenticationRequired` instead of spinning, routing the app to interactive re-login. The shared logout-and-expiry teardown is `connetto_client::teardown`: `purge_replica` (native) deletes the replica and its WAL and SHM sidecars but refuses when unsynced mutations remain unless forced, and `expiry_warning` plus `ConnettoConnection::unsynced` drive the proactive warning as an offline session nears its deadline with queued writes. The client learns its identity and deadline from the auth endpoints (never a second sync-wire field): the token pair, the loopback code redemption, and refresh all now carry `user_id` and `session_expires_at`, surfaced natively as `connetto_client::AcquiredSession` and in the browser as `connetto_web::BrowserSession`. Identity continuity was originally an in-replica stamp, and the generic-store plan's Phase 4 below replaced it with file selection. Proven by `connetto-server/tests/authn_flow.rs` (the responses carry a `user_id` and a positive `session_expires_at`, stable across refresh), `connetto-client/tests/native_auth.rs` (identity is continuous across a silent refresh and reacquire), `connetto-client/tests/authentication_client.rs` (a rejected handshake surfaces `ClientError::Auth` and the reconnect driver routes it to `AuthenticationRequired`), and `connetto-client`'s `teardown` unit tests (the purge blocks on unsynced data unless forced and the warning fires only near expiry with queued writes). The browser worker path is verified by the `connetto-web` wasm32 build plus clippy, with the headless-Chrome run offered separately.

## Generic auth store and the typed user id (phase 4 landed)

That work made the developer's distributed id type, not a string, the identity connetto carries end to end, and handed the auth tables to the developer. Phases 0 through 3 landed earlier: the generic diesel upserts, the `Id` generic through core and server, `ConnettoStoreSchema` plus `DbAuthStore<S>` and the `IdentityResolver`, and the mutation watermark re-keyed on `(user_id, session_id)` from the verified token. Its session plan is deleted, every phase having landed, and `plans/master-implementation-plan.md` carries what followed.

Phase 4 (the client identity pivot and the typed `user_id` wire boundary) is landed and green. Identity continuity moved out of the replica and into which file the client opens. `_connetto_identity`, `load_identity`, `stamp_identity`, `ConnettoConnection::bind_identity`, `ConnettoConnection::identity`, and `ClientError::IdentityMismatch` are gone. In their place `connetto_client::replica_db_name` names the replica from a SHA-256 over the id's own serde encoding, so the name is deterministic per identity and does not spell the id out in a directory listing. `DbWorkerConfig.replica_db_name` became `replica_db_prefix`, and `boot_db_worker` is now generic over the deployment's `Id`: it acquires the session first, derives the file, and only then opens a transport. That ordering is the fix for review finding D3, which had the worker resume the previous identity's replica over the wire under the new user's token before noticing the mismatch. It also retires the whole delete-and-rebuild path the old single-file design forced, and with it the sync-access-handle race the review flagged as G3, since nothing is deleted on a switch any more. Each identity keeps its replica: switching back resumes from its cursor with its unsynced work intact, and destroying one is an explicit data wipe rather than a side effect of another identity signing in, which is exactly what the per-replica encryption key in `docs/handoff-auth-at-rest-encryption.md` is scoped to support. Resident replicas stay plaintext until that lands.

Proven by `connetto-client/tests/native_auth.rs`, where a deployment whose `Id` is a `rosetta_uuid::Uuid` logs in through the real auth router over loopback and gets that exact typed value back from the token endpoint, and two identities derive distinct stable replica names, by `connetto-client/tests/authentication_client.rs`, where one identity's rows are invisible in the other's replica and survive the switch in their own, and by the `replica` unit tests for derivation, prefix collision, and encoding. The root gate, the `connetto-web` wasm gate, the three demo wasm builds, and the Docker-gated `authentication.rs`, `authn_flow.rs`, and `authn_db.rs` all pass. What none of that exercises is the browser under a real OPFS: the account switch there (deriving the file, opening it through the sahpool VFS, and leaving the other identity's file untouched) remains a headless-Chrome run, deferred.

## Replica encryption at rest (E0 through E5 landed, E6 step one landed)

The plan in `docs/handoff-auth-at-rest-encryption.md` encrypts each user's local replica under a per-replica key, and makes logout a set of composable primitives so an app can offer keep-my-data or wipe-my-data without connetto choosing a policy. E0 is committed as `e78f931`, E1 and E2 together as `5b3bfa9`.

Phase E0 (prototype the page codec) is DONE, and it changed the plan of record. The plan had called for a hand-written synchronous page-encrypting VFS layered over the sahpool VFS with RustCrypto AES-GCM. That was rejected: encryption in SQLite belongs in the codec layer, where page boundaries are known, not in the VFS layer, where they are not, and a VFS sees the main database, the rollback journal, the sub-journal, the WAL, and unaligned header reads through one pair of entry points with a different layout each. An off-the-shelf codec is available on both backends and needs no fork, no nonce scheme of connetto's own, and no `unsafe`: SQLCipher natively through `libsqlite3-sys`'s `bundled-sqlcipher`, and SQLite3 Multiple Ciphers in the browser through `sqlite-wasm-rs`'s `sqlite3mc` feature, which is the crate `connetto-web` already links. The construction is SQLCipher version 4, AES-256-CBC with a fresh 16-byte random IV on every page write plus a 64-byte HMAC-SHA512, both in 80 reserved bytes per page that SQLite itself accounts for, so no header page and no offset remapping. The browser codec must be pinned with `PRAGMA cipher = 'sqlcipher'; PRAGMA legacy = 4;` or it produces a different page layout and cannot read a real SQLCipher file. Proven in `examples/at-rest-encryption-spike` (a standalone workspace) by a native test run and a headless-Chrome run over real OPFS, plus a cross-backend check where the browser codec reads a file the native one wrote. The same phase confirmed the precondition E3 needs: the sahpool sync access handle is released synchronously when the connection drops.

E0 also moved the workspace to `libsqlite3-sys` 0.38.1. The 0.37 tree vendors SQLCipher 4.10.0 on SQLite 3.50.4, which predates `sqlite3changeset_apply_v3`, a symbol `diesel-sqlite-session` imports ungated, so the codec and the session extension could not coexist. That looked like an upstream cadence problem and was actually a pin: two ceilings, `<0.38.0` in the diesel fork's `future` branch and a caret `"0.37"` in `diesel-sqlite-session`, both since widened.

Phase E1 (the key store and provisioning) is landed and verified on both backends by real runs. `connetto_core::ReplicaKey` is the shared value type, 32 raw bytes and lowercase hex on the wire, zeroized on drop with `Debug` and `Display` redacted, and carrying no entropy source so the browser build stays free of one. The deferred escrow question is settled as provision-once with the server retaining nothing, because `AuthStore` has no device concept and a per-user server-held key would not be the per-replica key the plan locked. The server minted with `ring`'s `SystemRandom` at login and threaded `Option<ReplicaKey>` through `TokenPair`, `TokenResponse`, and `IssuedAuthCode`, `Some` on login and `None` on refresh. **E3 later amended this to device minting only, removing the wire field entirely. See the E3 entry below.** Custody is addressed per identity by `provision_replica_key(store, name)`, the real function name on both backends (two parameters, no wire parameter).

Phase E2 (wire encryption into the replica open path) is landed and verified on both backends by real runs, not by a compile. When E2 landed, the API was `connetto_client::Replica`, one value naming where the replica lives and whether its pages are encrypted: `Ephemeral`, `EncryptedFile { path, key }`, and `PlaintextFile { path }`, passed to `connect` and `connect_existing`. **E5 deleted `PlaintextFile`. `Replica` now has only `Ephemeral` and `EncryptedFile`.** Coupling storage kind to cipher is deliberate and was learned inside this phase: a first cut passed a separate `ReplicaCipher` beside `db_path`, and `Plaintext` then meant both a browser tab's `:memory:` mirror (nothing at rest, a key would encrypt heap pages against an attacker who already owns the heap) and a durable file left readable on disk. One spelling, opposite consequences. The enum makes the ephemeral case and the durable case separate variants, `Ephemeral` and `EncryptedFile`, so neither can be reached by omission.

`Replica::encrypted_file(path, resolved)` holds the one refusal: `None` yields `ClientError::ReplicaKeyMissing` rather than a silent plaintext file. That closed the phase's other defect, an asymmetry where the browser worker refused a missing key while natively nothing did, so plaintext-while-logged-in was reachable both through the template constructor (which hard-coded it regardless of authentication) and by simply passing the plaintext variant to `connect`. The worker now calls the same function, and the template constructor was renamed `connect_with_plaintext_template` so the fact it cannot encrypt reached its callsite. **E5 deleted `connect_with_plaintext_template`.**

`PlaintextFile` had exactly one justified use: **a deployment with no authentication configured**. An authenticating deployment reaching it was always a bug. **E5 deleted the variant.** The unauthenticated replica is now encrypted under a device-scoped key, provisioned by `storage::device_key` at boot, so there is no longer any path where a durable replica is plaintext.

Two things E2 measured rather than assumed, both of which changed the design. First, `unlock` probes that a page codec is actually linked, because in a codec-less SQLite `PRAGMA key` is an unrecognised pragma that succeeds silently and leaves every page in the clear: natively the probe reads `PRAGMA cipher_version`, and in the browser it asserts that a bogus cipher name is rejected, since sqlite3mc reports pragma failures through the VFS shim while vanilla SQLite says nothing. That silent-success mode is why the codec is a hard dependency of `connetto-client` on both targets instead of a feature. Second, an `ATTACH` does not inherit a key the way the plan expected. A database created through an `ATTACH` on a keyed connection inherits the main database's key salt, and an `ATTACH` of an existing database applies the main database's derived key regardless of any `KEY` clause, so a tier file created by any other connection carries a different salt and will not decrypt. The consequence is that a durable native tier must be first-booted through the replica connection, which is what `attach_local_tier_ddl` now does for any path rather than only `:memory:`, and `attach_local_tier` keeps working on every later run because the first boot made the salts agree.

The baked tier template is retired, and the reason is worth stating precisely because it is easy to misread as a capability gap. The page codec is always linked, on both targets, unconditionally: encryption support was never in question. What is missing is a *conversion*. A template is a finished plaintext database image and the per-replica key does not exist until a device logs in, so an encrypted template cannot be baked and first boot would have to convert a plaintext one. Both candidate transforms exist on opposite sides: `sqlcipher_export` appears ten times in the SQLCipher amalgamation and zero times in the sqlite3mc one, and `PRAGMA rekey` encrypts a plaintext database on sqlite3mc but explicitly cannot on SQLCipher. Each backend has one of the two and they are different ones, so there is no single code path. DDL works identically on both and the replica already used it, so `DbWorkerConfig.frontend_template` became `frontend_ddl`, `WorkerStorage::import_db` is gone with the `import_db_unchecked` question, and the demos' `build.rs` emits the translated DDL beside the template it still bakes for pg2sqlite's document validation. `connect_with_replica_template` is renamed `connect_with_plaintext_template` so the fact reaches its callsite. This is a deviation from E2's written acceptance, which had listed a baked-template first boot on an encrypted replica: the criterion was retired rather than met, because a template is a migration problem and the migration is the part that is not portable.

An undecryptable replica is its own error rather than a corruption report: `ClientError::ReplicaUndecryptable`, whose reachable benign cause is a device whose key store was cleared while its file survived. There is no unsynced-mutation guard on the discard and there cannot be one, since the pending mutations live inside the file the key will not open, so the recovery is `purge_replica` with `force` and a fresh connect. In the browser, `boot_db_worker` threads the resolved key into both the replica and the tier connection and refuses to boot when auth is configured but no key resolved, rather than opening a plaintext replica an app believes is encrypted.

`RefreshStore` was left plaintext by E2, and the blocker was structural: it is read to learn the identity, while the per-replica key is addressed by the name derived from that identity, so it must be readable strictly before any per-replica key exists. **E3 closed this**, because device minting supplied the missing piece: a device-scoped key named by a literal rather than by an identity, with no ordering problem against the store it protects.

Native acceptance is `connetto-client/tests/encrypted_replica.rs`, five tests against real files: an encrypted replica whose bytes carry neither the SQLite magic, the row value, nor the schema text while a plaintext control keeps all three, a fresh connection with the cached key that reads the rows back and still holds its unsynced mutation, a wrong key that surfaces as `ReplicaUndecryptable` and a forced purge that lets the next connect rebuild, a durable tier that is ciphertext and re-attaches on a second run, and a tier file from any other connection that fails to attach rather than being left readable. The browser half is `connetto-web/tests/encrypted_replica.rs`, five tests VERIFIED under headless Chrome against real OPFS: the same ciphertext-at-rest assertions read back through the pool's own export with a plaintext control, a wrong key and an unkeyed open that both fail, the tier as its own independently salted connection under the same key, and the synchronous release of the sahpool access handle when an encrypted connection drops, which is the precondition E3's wipe rests on. The E1 key-store suite still passes alongside it.

One browser constraint the run made concrete: `sqlite-wasm-rs` allows one connection per database, and the sahpool VFS keys its open-file bookkeeping by name, so two live connections to one OPFS file trip a `debug_assert` in its `xClose`. connetto never holds two, and a test that did was the only thing that hit it. The same run also showed `mcIoClose` in the stack for a bare file name, confirming that sqlite3mc wraps the default VFS and a plaintext open passes through the codec shim unconfigured rather than bypassing it.

Phase E3 (the logout primitives and the purge wiring) is landed and verified on both backends by real runs, not by a compile.

It amended a locked decision. The per-replica key is now **device-minted**, not server-provisioned: `replica_key` is gone from `TokenPair`, `TokenResponse`, and `IssuedAuthCode`, `AuthError::KeyGen` and the server's `ring`-backed mint are gone with it, and the client mints instead (`connetto_client::provision_replica_key`, `connetto_web::auth::provision_replica_key`). The requirement is unchanged, per-replica scope with local caching and offline usability, and the mechanism was disposable: a build that already trusts its local RNG for the PKCE verifier, the CSRF state, and the AES-GCM IV that wraps this very key cannot coherently refuse to trust it for the key. The gain is that no key material crosses the wire in either direction, so `AuthCodes` is no longer a window in which the server holds any. Minting deliberately does **not** replace the missing-key refusal: `provision_replica_key` is for a replica being created, an existing one reads `ReplicaKeyStore::load`, and a `None` there still yields `ClientError::ReplicaKeyMissing`. Minting for an existing replica would hand back a key that decrypts nothing and would fill the record a restored backup could still occupy, which would defeat the "back up the key" recovery E2 endorsed.

Logout is now real on both backends. `POST /auth/logout` is RFC 7009 shaped: the refresh token authenticates the request as well as naming the session, so no valid access token is needed and an expired one does not block a logout, and the endpoint always answers `204` so it cannot be probed. It is backed by `AuthStore::session_for_refresh`, which verifies the presented secret in constant time without rotating, and `AuthService::revoke` finally has a caller. `NativeAuthenticator::logout` and `BrowserAuthenticator::logout` are credential teardown, `teardown::wipe_replica` and `connetto_web::storage::wipe_replica` are data teardown, and `teardown::forget_device` is the one convenience. **Logout awaits the revoke and the local clear happens either way**: `Ok` means the session is refused at the next handshake, an error means local state is gone while the session stays live until it expires. Fire-and-forget would hide that difference and queueing is not expressible, since after the clear there is no credential left to authenticate a revoke with.

Two orderings carry the reasoning. The unsynced guard runs before the credential is destroyed, because once the refresh token is gone the queued writes can never be uploaded and a later guard would protect nothing. Inside a wipe the key dies before the file, so a failed delete leaves inert ciphertext rather than a readable database, at the cost of a leftover that reports `ReplicaUndecryptable` and recovers through a forced purge.

The browser purge is the new public `connetto_web::storage` module: `ReplicaStorage` (the old private `WorkerStorage`) with `install`, `exists`, `list`, `vfs_name`, `db_url`, and `delete_db`. `RefreshStore` is no longer plaintext: it is encrypted under a device-scoped key (`storage::device_key`), which device minting unblocked, since that key is named by a literal rather than by an identity and so has no ordering problem with the store it protects. A store that will not open is discarded and forces a fresh login, which is what `boot_db_worker` now does. There is deliberately no browser `forget_device`: the replica connection lives inside the relay hub's pump for the worker's whole life, so nothing outside `boot_db_worker` can drop it, and a wipe needs it dropped first. That asymmetry is recorded on the module rather than left to be read as an oversight.

**E5 deleted `Replica::PlaintextFile` and `connect_with_plaintext_template`.** E3 had left them with a named blocker: two consumers first-booted from a plaintext template and no plaintext-to-encrypted transform existed in the browser codec, so retiring the baked replica template had to come first. E5 completed that retirement and the deletion together.

**E4.a is the shared OAuth spine against a real identity provider, natively and in-process.** The dance is one implementation for both clients, so proving it once proves it for both, and it has never run: every test to date uses `PermissiveProvider`, which performs no I/O, or `GenericOidcProvider::from_endpoints`, which is documented as taking no network, so discovery, the token exchange, and the JWKS fetch have never executed and the authorize endpoint has never been hit. E4.a is **DONE**, in `crates/connetto-server/tests/oidc_spine.rs` (three tests). The spine test asserts every hop of the dance against `oauth2-test-server` on a real loopback socket, ending at a connetto session the real handshake verifier accepts, with the `user_id` checked against what `deterministic_uuid` derives from the issuer and subject the provider asserted. Three findings came out of running it. The nonce check turns out to be unreachable from the HTTP surface, because the per-login PKCE verifier refuses a crossed code at the token exchange first, which connetto renders as `502`, so the test that was written to prove the nonce was corrected to pin the guard that actually fires. `oauth2-test-server` publishes `localhost` in its discovery document while binding `127.0.0.1`, and `openidconnect` rightly refuses a document whose issuer does not match the URL it came from, so its host is pinned to the dialed address. E4.b is **DONE for the worker path**. The test is `examples/wasm-smoke/tests/browser_auth.rs`, in a dedicated worker under headless Chrome, in the stack-up suite because it needs an external process, and it needs no Postgres. First execution of the entire browser acquisition path: `acquire` asks for a login, the login completes against the real provider, `complete` redeems the code over `web-sys` `fetch`, the rotated refresh token lands in OPFS encrypted under the device key, a second `acquire` refreshes silently, the identity names a device-keyed replica that opens, `logout` clears local state, and a credential copied before the logout no longer refreshes. **E4.c is the demo keep-versus-wipe prompt**, moved out of E3 by confirmation and reusing E4.b's stack. Its one open API question is now settled: exercising wipe mode through the real worker needed a way to stop the relay hub and drop the replica connection, since the OPFS delete cannot run against a live one, and rather than growing `RelayHub` a shutdown plus `boot_db_worker` a return handle, the wipe is deferred to the next boot where nothing is open yet. `storage::mark_wipe_pending` records the request in its own `IndexedDB` database and `boot_db_worker` drains every outstanding record with `take_pending_wipes` and wipes at the very start, before the login and before anything opens, which is also crash-safe: a tab closing mid-wipe leaves the wipe to the boot after that rather than half done. Two placement mistakes were caught before this landed, both fixed by the same move. Looking the record up by the current identity meant the wipe would only fire on a boot where that same person logged in again, so anyone who asked for a deletion and never returned would keep their data. And sitting after acquisition meant it waited behind an interactive login, which is precisely what a logout forces. Records name their own replica, so no identity is needed to act on one, and the drain now runs first. The unsynced guard moves to the marking, because at boot the replica is closed and its queued writes are unreadable, while at the prompt the connection is open and the credential still works. Three more tests in the gated `connetto-web/tests/teardown.rs` cover it, now seven in that suite. What remains of E4.c is the demo prompt, which needs four processes up and a browser drive.

Two constraints E4 surfaced by reading, both of which live in the browser branch. The browser auth path assumes `/auth/*` is same-origin with the app: the OAuth dance needs no CORS at all, since every step is a navigation or a server-to-server call, but connetto's own `POST /auth/token`, `/auth/refresh`, and `/auth/logout` are worker `fetch` calls, and this repo's demo topology puts the app and auth on different ports. It went unnoticed for two phases because with `auth` unset the demos make zero HTTP requests to connetto-server, only a WebSocket, whose handshake is not CORS-governed. And `PermissiveProvider` cannot be completed by a real browser, because its authorize URL is literally `about:blank?state=...`, which `native_auth.rs` never noticed since its fake browser walks the redirect chain with HTTP calls instead of navigating.
