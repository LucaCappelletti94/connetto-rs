# Prompt: authentication (OAuth 2.0 / OIDC) architecture design

Read `docs/handoff-oauth-authentication.md` first and in full. It is the authoritative spec: the exact gap with file and line references, the current code seams to build on, the questions the design must answer, the dependency evaluation mandate, the traps, and what done means. This prompt is only the kickoff.

The objective is to write a technical architecture document, not code. Produce `docs/architecture/11-authentication.md` describing how authentication (OAuth 2.0 / OIDC) will work across connetto in a general, reusable form: the trust boundary, the token flow, server verification, client acquisition for both the native and wasm frontends, offline-first token expiry, the dependency choices, and any upstream or fork work required. Do not add a crate to any manifest and do not implement the mechanism this session.

Scope it precisely. This is authentication (proving who a caller is), distinct from authorization (which rows they may see or write), which already lives in `docs/architecture/08-authorization.md`. The one connecting fact is that the verified identity becomes the session `AuthContext`, which the authorization layer and Postgres RLS (`set_config('app.user_id', ...)`) already consume. Today the server ignores `Handshake.auth_token` and trusts the client-supplied id (`crates/connetto-server/src/session.rs`, `run_handshake`, around line 771), so any client can assume any identity. Closing that end to end, from client token acquisition to server-side cryptographic verification, is the design's reason to exist.

Ground every dependency claim. Name concrete candidate crates (server: `openidconnect`, `jsonwebtoken`, `oauth2`, a JWKS fetcher, an async HTTP client that fits the tokio and diesel-async stack; native client: `oauth2` or `openidconnect` plus OS secure storage; wasm client: whatever actually cross-compiles to `wasm32-unknown-unknown`) and put them in a tradeoff table whose every capability or cost cell is verified against the crate's source or documentation before you present it. Mark any unverified cell as unverified. The wasm cross-compilation of an OIDC or OAuth crate is the primary risk and the most likely uphill, assess it directly and, if a fork is warranted, capture it as a proposal in the repo's `upstream-*.md` convention without implementing it.

Standing rules: ASCII punctuation only in all prose (no semicolons, no em or en dashes, no ` - ` as punctuation). The document goes in `docs/architecture/`. Prefer the long-term optimal design over shortcuts, if an interim step is unavoidable mark it as interim and name the optimal target it leads to. Cross-reference `02-protocol.md` (the handshake), `06-reconnect.md` (offline and reconnect), `08-authorization.md` (the authZ boundary), and `09-wasm.md` (the browser topology). Add an authentication open question to `docs/architecture/open-questions.md` and add a short pointer from `docs/roadmap.md`.

Out of scope: writing code, adding dependencies, changing the wire protocol unless the design genuinely requires it (and then only as a specified proposal), and redesigning the authorization model.
