# Prompt: aggressive, precise, impartial review of the authentication implementation

Read `docs/handoff-oauth-review.md` first and in full. It is the authoritative brief: the code map across all six phases and four crates, the baseline gate to reproduce green, what is runtime-proven versus compile-only, the specific open questions to scrutinize, the deduplication candidates, and what done means. This prompt is only the kickoff.

The objective is to review the authentication code (OAuth 2.0 / OIDC, phases 1 to 6 of `docs/architecture/11-authentication.md`) and produce a findings report, not to fix anything this session. Write `docs/review-oauth-authentication.md`. For every finding give the file and symbol, what is wrong or smells wrong, the severity (correctness, security, maintainability, style), why it matters, and a concrete suggested change. Separate confirmed defects from open questions from taste, and end with a short prioritized list.

Be impartial and evidence-first. Do not trust the author's roadmap paragraphs (`docs/roadmap.md`) or the memory notes, they state intent, and intent is not fact. Verify every behavioral claim against the actual code. Treat `docs/architecture/11-authentication.md` as the contract and check the implementation against its principles (asymmetric-only, `iss` and `aud` pinned, `none` rejected, authentication gates sync not local reads, one sync-wire addition only, refresh-token lifetime defines replica lifetime, resume requires the same identity, logout and expiry share one teardown). Where code and prose disagree, the code is the fact and the disagreement is a finding. The scrutiny list in the handoff is a set of open questions, not a verdict: confirm or refute each from the code, do not assume a listed item is a bug or that an unlisted area is clean.

Cover the full surface, not just the freshest work. Phases 5 and 6 (the browser worker and the offline teardown) are the least runtime-proven and deserve weight, but the real security load sits in phases 1 to 4: the JWT pinning in `token.rs`, the refresh rotation and reuse-is-theft and the revoke-outside-the-aborted-transaction handling in `store.rs`, the PKCE verify and one-time-code redemption in `http.rs`, and the openidconnect client build and Microsoft any-tenant matcher in `provider_oidc.rs`. Assess test quality too: whether `authentication.rs`, `authn_flow.rs`, `provider.rs`, `authn_db.rs`, `native_auth.rs`, `authentication_client.rs`, and the `teardown.rs` unit tests defend observable contracts or merely exercise plumbing.

Weight findings by what you can actually verify. The `connetto-web` browser worker path is compile-only (no headless-Chrome run has exercised login broadcast, OPFS refresh persistence, or the account-switch purge and rebuild), the Docker-gated `authn_db.rs` was not re-run after the phase-6 store change, and provider verification has never run against a live IdP. Flag anything that can only be caught at runtime as such rather than asserting it works or fails. Before reviewing, reproduce green so a finding is about the code and not a stale tree: `cargo +stable fmt --all -- --check`, `cargo +nightly clippy --all-targets --all-features -- -D warnings`, and `cargo +stable test --release --all-features` at the root, plus fmt and `cargo +nightly clippy --target wasm32-unknown-unknown --all-targets -- -D warnings` from `crates/connetto-web`.

Standing rules: ASCII punctuation only in all prose (no semicolons, no em or en dashes, no ` - ` as punctuation). `cargo +stable` for build and test, `cargo +nightly` for clippy only. Do not commit, push, or open anything, this is a review. Do not run the Docker-gated tests or a headless-Chrome session without explicit approval.

Out of scope: fixing the code (report only unless asked to fix afterward), redesigning the authorization model in `docs/architecture/08-authorization.md`, and any commit, push, or deploy.
