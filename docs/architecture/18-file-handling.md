## Purpose

Applications handle files: a photo attached to an entry, a dataset a scientist collected, a document. Rows are the wrong vehicle for their bytes, so file handling is its own subsystem: metadata travels as ordinary synced rows, content travels on its own channel with its own storage, and the boundary between the two is this chapter's subject.

## The boundary

**Decided (R24, concluded 2026-08-21).** connetto-core does not build file handling. The boundary is the crate, not the repository: the file crates live in this repository beside the demos, depend on connetto and never the reverse, and the demos carry the feature end to end per R54's rule. `connetto-core` deletes the old unimplemented `FileStore` trait and gains exactly one seam, the signer trait described under Tickets below (**Decided (R66)**).

**Amended (R69, 2026-09-12): "never the reverse" binds the libraries, and the shipped executable serves files.** `bin/connetto-server.rs` takes `connetto-file-server` behind a default-on `content` feature, mounts the four file routes beside its websocket and auth listeners, builds the ticket signer and verifier from one keypair in `main` so no key crosses a process, gives the file router its own admin and reader pools so uploads never compete with the change stream for the owner pool, and runs the sweep on a cadence. `CONNETTO_CONTENT_URL` unset keeps today's `NoSigner` and no routes. No connetto library depends on a file crate. Rejected: a leaf crate holding the executable to keep the sentence as written, and a second process now, which every demo and CI stack would start for a scale nobody has. A file-only executable over the same `Config` is additive the day a deployment scales files out.

**Decided (R69, 2026-09-12): a browser tab stages by attaching the bytes to its own mutation.** The tab computes the file identity itself, writes the metadata row on its mirror as an ordinary captured mutation, and the bytes ride the tab's internal wire as an attachment, a `Blob` that crosses to the worker without a copy. The worker runs `stage` with the tab's changeset as the row closure, so the manifest, the outbox entry and the row commit in one transaction exactly as natively, and a file identity that disagrees between tab and worker rejects the whole mutation through the existing rollback path. Resolving is a correlated request on the same wire answered with a signed URL, a `Blob` the tab turns into an object URL it owns, or unavailable. The server protocol is untouched. Rejected: staging in the worker first and writing the row after, two transactions where a crash between them strands an outbox entry whose ticket is refused forever, and sending SQL beside the bytes, a second write vocabulary.

The file crates own the traits with more than one implementation: `ChunkStore` (`write_chunk`, `read_chunk`, `has_chunk` and `delete_chunk` by content hash, with OPFS, `std::fs`, in-memory and object-store implementations), the application-facing content resolver, and the pin policy (**Decided (R64, R67)**).

**Amended (R67, 2026-09-08): `delete_chunk` joins the three original methods, and `ManifestStore` is not a trait.** The delete is what makes an unpin reclaim anything: without it a client that pinned a dataset once holds it forever, and the store is the only thing that can remove a chunk file. A store never decides that a chunk is unreferenced, because two manifests can name the same chunk, so that judgement stays with whoever holds the manifests. `ManifestStore` was named here as a trait and has exactly one implementation on each side of the wire, three typed tables in the replica on the client and three in Postgres on the server, so it is those tables rather than an abstraction over them. R79's peer source is the case that would have needed a second implementation, and it needs a content source rather than a manifest store.

**Amended (R67, 2026-09-09): `ChunkInventory` sits beside `ChunkStore`, and enumeration is deliberately not on it.** A store that can list what it holds implements the second trait, and the client's `std::fs` store, the in-memory store and R68's OPFS store all can. A deployment's object store is not asked to: it holds every file every caller ever uploaded, so answering "all of it" as one list is the wrong shape at that size, and the server sweeps from its chunk registry, the index it already keeps. This is the distinction the earlier rejection of a second storage trait turned on. Delete belongs on `ChunkStore` because a store that can be written and not pruned is a store whose disk only grows, and every store can prune. Enumeration is not universal in the same way, so a bound that demanded it of every store would be a bound the object store could only satisfy badly. Rejected: a fifth `ChunkStore` method, for that reason; and a durable staging record written before the chunk files, which cannot close the gap it exists for, because it would have to name hashes that only chunking produces.

## Identity, chunking, and the manifest

**Decided (R64).** A file's identity is the plain BLAKE3 hash of its bytes, computed in the same streaming pass as chunking. The identity is deliberately chunking-independent: BLAKE3 is internally a Merkle tree, so verified range streaming (bao) remains a later upgrade with no format change, anyone can recompute the identity with `b3sum`, and re-tuning chunk sizes never re-identifies a file. Rejected: a hash over the chunk hashes, whose identity silently depends on chunking parameters.

Content is split by FastCDC under a per-mime-class parameter table shipped as data, and a file at or under the maximum chunk size skips chunking. Compressed formats (JPEG, video, gzipped scientific data) get large parameters or whole-file treatment because sub-file dedup finds nothing in them. The manifest is the ordered list of per-chunk (BLAKE3, length) pairs, transport and dedup metadata only, lengths present because they map a byte range to chunks.

Each chunk is zstd-compressed (level 3, per-mime skip table, a compression flag in the chunk header) between chunking and encryption, the Borg and Kopia order: the dedup hash is always over plaintext. Text-heavy scientific data roughly halves under zstd, and the driving use case is exactly that.

## Client storage

**Decided (R24 position 3, R64, R67, R68).** One encrypted chunk store outside SQLite: chunk files in OPFS in the browser and plain files on native, each encrypted with XChaCha20-Poly1305 under a random 24-byte nonce stored with the ciphertext, the chunk's plaintext hash as authenticated associated data, and the key derived by BLAKE3 key derivation with a purpose label (decided 2026-09-02, superseding the HKDF wording: one hash family, zero extra dependencies) from the same custody `ReplicaKeyStore` serves, so the R23 unlock gate and crypto-shred-on-wipe cover content exactly as they cover the replica. XChaCha was chosen over AES-GCM at review: the 192-bit nonce removes the birthday bound and the AES-NI assumption on mobile cores, and the cipher is one shared pure-Rust layer on every target where the replica cipher is two (SQLCipher native, sqlite3mc wasm).

**Amended (R67, 2026-09-08): the manifests and the upload outbox live in the replica, not in the device-private tier.** They are committed in the same transaction as the entry row, so a crash orphans a chunk file (collected by sweep) but never commits a row pointing at bytes that were never written. SQLite never carries content bytes on either side of the wire.

The tier cannot hold them, because the invariant and the tier are incompatible and the incompatibility is silent. The replica is opened `PRAGMA journal_mode=WAL` before the tier is attached, so the two are separate files and SQLite's atomic commit spans attached databases only while no database in the set is WAL. Measured: a transaction writing both files commits with no error, and a host crash inside that commit may update one file and not the other. Manifests carry the `_connetto_` prefix that already marks connetto's own bookkeeping in the replica, beside `_connetto_meta`, `_connetto_pending` and the subscription set, which keeps them out of capture, out of the tier's application-table listing and off the wire. This is R20's correction applied to the same problem, and it carries R20's second reason too: the tier is optional and defaults to absent, so a tier-resident manifest would make file handling unavailable to any client that did not ask for one. It also gives R68 its archive step for free, since the R26/R56 archive exports the replica. Rejected: keeping them in the tier and dropping the invariant for a sweep of manifests with no row, because the reverse case is unrecoverable, a row naming a `file_id` whose chunk files are all present but whose chunk list and order are gone, which is the production failure the invariant exists to prevent, merely rarer. Rejected: putting the tier in WAL as well, which loses cross-file atomicity for exactly the same reason.

Client content divides into two classes. Unsent content, authored here and not yet uploaded, is data: its chunk files travel in the R26/R56 archive by manifest walk, because an unsent write cannot be refetched. Fetched content is cache: evictable under pin rules, never exported, refetchable by construction. The rejected alternatives (all chunks as encrypted-tier blobs, all chunks in plaintext OPFS, and a provenance split routing unsent bulk into SQLite) are recorded in the plan's R24 section.

**Decided (2026-09-14, before R69): a data wipe removes the content store with the replica, on both platforms.** The store is one more thing the replica key opens, so it is on the list chapter 14 keeps under Teardown, and it is found by derivation like the tier: `db_path-content` natively, where the demos build their `FsStore`, and in the browser the per-account namespace `sha256(seed, replica_db_name)` that the pending-wipe record carries. The namespace being per account is what makes the removal safe: no second identity on the device can hold chunks under it, and an anonymous boot opens none.

**Amended (R68, 2026-09-10):** the browser store belongs to the dedicated database worker and reacquires its `OPFS` root for each operation. A new chunk closes under an unreportable temporary name before an atomic move exposes its hash, and opening the namespace removes interrupted temporary names. An existing hash is replaced through `createWritable` and `close`. Environmental `OPFS` failure selects worker-lifetime memory, while an invalid namespace fails installation. That fallback refuses writes, because the replica would record a manifest and an outbox entry for bytes that die with the worker and the next boot would find them gone, and it holds nothing durable either, so every read misses. A missing read there is inconclusive rather than a loss, which is what preserves the outbox entries whose bytes are sitting in an `OPFS` namespace this run cannot open. A store the application chose as ephemeral accepts its own writes, because nothing there claims durability. An anonymous run always selects memory so the bare replica name never leaves durable content. An authenticated namespace is the lowercase SHA-256 of the configured seed and replica identity, preventing account switches from opening ciphertext under the wrong key. A destructive logout persists that exact namespace even when the current backend is memory, and the next worker removes it recursively once the key, the tier and the replica are gone.

**Amended (R68, 2026-09-10):** version 3 device archives declare every entry and its per-entry encoding. Unsent content travels as plaintext `content/manifests.json` plus one `content/chunks/<hash>` entry per distinct chunk, while fetched and pinned cache stays behind. Import validates the exact ZIP layout, lengths, hashes and reconstructed file identities before writing through the receiving `EncryptingStore`, then commits application changes, manifests and outbox entries in one SQLite transaction. A connected importer replays the restored mutation queue before the content driver can request visibility-gated upload tickets. A generic importer refuses nonempty attachments, and the content importer refuses any path outside `content/`, rather than silently discarding required data. Attachments must use ZIP `Stored`, with a 256 MiB per-entry ceiling and a 2 GiB aggregate ceiling checked before export writes any ZIP entry and before import reads an attachment body.

**Amended (2026-09-12):** Each compressed row entry (`synced.patchset`, `device-private.patchset`, and `pending.changesets`) decompresses through a streaming decoder bounded at the 2 GiB ceiling the attachment aggregate already names, applied per entry rather than in aggregate, so the two paths share one figure for what an archive may ask a device to hold in memory.

**Decided (2026-09-14, before R69): an archive costs one chunk of memory, in either direction, on either platform.** The archive was held whole three times over on import, the ZIP bytes, the decompressed attachments inside the replica plan and a copy of every chunk in the content plan, and three times over on export, the decrypted chunks, the ZIP and the copy that crosses to the tab. A wasm32 linear memory is at most 4 GiB, so a conforming 2 GiB archive could not exist in the worker and the advertised ceiling was a number no browser could reach. Instead the archive reader takes a seekable source and yields entries one at a time, the content importer writes each chunk through the encrypting store as it is read, the archive writer takes a plain `Write` sink through `ZipWriter::new_stream`, which writes data descriptors instead of seeking back to patch headers, and the exporter reads each chunk from the store as its entry is written. Attachments name their entries and no longer carry bytes. In the browser the import source is the tab's `Blob`, which crosses `postMessage` without a copy and is read through `FileReaderSync`, the one synchronous seekable read a dedicated worker has, and the export sink is a `Blob` grown by concatenation, which the browser keeps as a list of parts and spills to disk on its own, so no temporary file exists and nothing is left to clean up. Natively both ends are files. The 2 GiB aggregate and the 256 MiB per entry stay as the bounds on what an archive may ask a device to hold on disk and in one chunk respectively, and the amendment above that made the aggregate a memory figure now describes the per-entry decoder alone. Rejected: keeping whole archives in memory and moving the bytes instead of copying them, which leaves a conforming archive unimportable on wasm32 and forces the ceiling down with it, and an OPFS temporary file as the export sink, whose `File` the tab holds for a time the worker cannot know, so it needs an exports directory, an acknowledgement and a boot sweep for what a `Blob` gets for free.

**Amended (R68, 2026-09-12): what the worker relay serves in every situation it can be in.** R68 made the recovery loop serve requests it had refused on `main`, and the list of situations it handles was never written down, so sixteen review findings were each one line of this table. The table is the list. A cell says whether the request is served where it arrives, held until the upstream is back, or refused because the hub has ended.

| Request | Connected | Sleeping before retry | Connecting | Attaching | Replaying subscriptions | Closed |
|---|---|---|---|---|---|---|
| `Attached` | Served | Served | Served | Served, no interruption | Served, no interruption | Refused |
| `Frame` | Served | Held | Held | Held | Held | Refused |
| `Gone` | Served | Served | Served | Held | Held | Refused |
| `Kill` | Served | Served | Served | Held | Held | Refused |
| `Unsynced` | Served | Served | Served | Served, interrupts | Served, interrupts | Refused |
| `Export` | Served | Served | Served | Served, interrupts | Served, interrupts | Refused |
| `Import` | Served | Served | Served | Served, interrupts | Served, interrupts | Refused |
| `ForgetRetired` | Served | Served | Served | Served, interrupts | Served, interrupts | Refused |
| `RefusedContent` | Served | Served | Served | Served, interrupts | Served, interrupts | Refused |
| `RetryRefused` | Served | Served | Served | Served, interrupts | Served, interrupts | Refused |

A frame is held in every recovering situation because a write or a subscribe needs the server, and it is the only request that does. An attachment is served everywhere because registering a tab writes hub state and nothing else, and the tab's own announce gives up after fifteen seconds, so holding it fails a healthy tab for the length of an outage. A departure and a kill unsubscribe upstream, so they are served while the connection is idle and held while the attach owns it, where nothing waits on them. The six requests that answer from the replica interrupt an attach rather than wait for it, and the interrupted attach resumes on the installed transport afterwards.

One order rule covers every served cell. A request that would be served where it arrives is queued instead while any older request is already queued, and the queue drains in arrival order once the upstream is back, so a kill can never overtake a frame of the tab it kills. Refused means the intake has closed and the hub has ended, so every waiting reply sender drops and its caller reads the hub as gone.

| Background job | Runs while | Held while | One turn is | Interrupted by |
|---|---|---|---|---|
| Outbox upload | Connected | Sleeping, connecting, attaching, replaying | One sendable entry, the one after the last attempt | A served request across its transfer, and a ticket wait that yields |
| Content ticket retry | Connected | Sleeping, connecting, attaching, replaying | One ticket request for the deferred entry | Queued local work, which takes the turn |
| Integrity walk | Connected, sleeping, connecting | Attaching, replaying | Eight chunks of the head file | Every other source, because the walk is one branch of the same wait |
| Orphan sweep | Connected, sleeping, connecting | Attaching, replaying | One listing, then eight deletions | Every other source, and a failure waits for the retry timer |

The upload and the ticket retry need a ticket the server mints, so they cannot run while the upstream is down and the table states that rather than leaving it to be rediscovered. The walk and the sweep read only the replica and the chunk store, so they run through the retry sleep and the connect, which is when a device is most likely to sit for a long time. They stop while the attach and the subscription replay own the connection, because the walk reads the replica through it.

**Amended (R68, 2026-09-12): what a commit invalidates.** A resumable job carries a decision taken over state a later commit can change, so each commit says what it invalidates rather than each job guessing.

An import commit invalidates four things: the scan cursor, because the import can restore the chunk an earlier slice found missing, so the current file is scanned again; the orphan list, because a listed chunk can be exactly what the import wrote, so the list is taken again; the sweep schedule, which is owed a turn again because a failed import leaves chunks nothing names; and the outbox wake, because the restored writes and files are queued. A scan cursor is bound to the file and to a fingerprint of its ordered chunk list, so a manifest replaced under the same identity starts again even without this invalidation, and a retirement is decided by reading the missing chunk again at the end rather than by what a slice saw.

An upload success schedules two things: the retention pass, because an uploaded file is no longer unsent and nothing else releases it, and the next outbox attempt from what the walk left. A failed sweep keeps its turn owed and waits for the upload retry backoff rather than the next cycle, because a sweep lists everything the store holds and retrying that in a loop is worse than waiting. A retirement keeps the file identity in `_connetto_content_retired` until the application acknowledges it, because the dequeue destroys the only record that this device declared the file.

**Amended (fix/outbox-liveness, 2026-09-13): clearing a refusal wakes the outbox driver.** The outbox driver schedules walks from the sendable count, which excludes refused entries, so a refused file never triggers a walk on its own. When the application clears a refusal, the driver is notified exactly as an import notifies it, so the cleared entry is attempted without waiting for a reconnect, a mutation, or a new import.

The worker relay runs the content integrity pass at boot and retries its outbox after import, reconnect, mutation acknowledgement, and backoff. Retiring an outbox entry destroys the only record that this device declared the file, so the identity is written to `_connetto_content_retired` in the same transaction as the dequeue and reported by every pending-work answer until the application acknowledges it, which survives worker restarts because the record is in the replica. Each wake attempts the entry after the one the last wake took, so a file whose ticket keeps being refused cannot starve the rest of the outbox. A ticket wait uses the connection's cancel-safe pump, returns unrelated upstream events to the relay, and yields to queued local relay work while remaining resumable, so a refused or slow mint cannot hold a tab's request.

**Amended (fix/outbox-liveness, 2026-09-12): a permanently refused upload stays in the outbox, marked with its refusal detail, and is not attempted again until the application asks.** Two reasons. The chapter already says presence in the outbox is what makes content unsent rather than cached, and a refused file is exactly that, so every consumer that reads the outbox, pending work, the export walk, the wipe guard and the device tier inherits the right answer with no change. And a refusal is a fact about the deployment's configuration rather than about the file: the ceiling lives in the ticket the deployment mints, R66 made part of it per identity through the rolling bandwidth rate, and R87 adds a per-identity quota, so an operator raising a budget or a person freeing space makes the same upload succeed. The cost, stated rather than hidden: the outbox now means not yet sent rather than will be sent, so every count includes refusals and a caller that wants only the sendable entries asks for those. A file too large for its deployment sits there and blocks a non-forced delete until the application retries it, drops it, or the person forces the delete. Rejected: a reason column on the retired table with the wipe guard reading it, which teaches four consumers to read a reason and forfeits the retry; and treating every retirement as blocking a delete, which blocks erasing bytes that are already gone.

**Decided (2026-09-14, before R69): a permanent upload outcome is one of two events, and which one is decided by where the fact comes from.** A refusal is an answer from the server, `400`, `413`, `422`, an undecodable reply or a malformed grant, so the entry stays in the outbox under the amendment above and the application sees `UploadRefused`. A loss is a fact about this device, a manifest the outbox names that the replica no longer holds or a chunk the store cannot read, so the entry is retired and the application sees `BytesLost`. The integrity scan already retires a missing manifest, and the upload walk retires it the same way rather than routing `NoManifest` through the refusal path, where a retry on request could only fail identically. The event the application receives for one fact is therefore the same whichever pass found it first.

## Display is not sync

**Decided (R24 position 2).** The common case renders a short-lived signed URL and never touches client chunk storage: the file server assembles from chunks and serves plain HTTP with `Range` mapped through the manifest, a strong `ETag` equal to the content hash, and immutable caching, so the browser's own cache, progressive rendering and video seeking do their jobs. Local content sync happens in exactly three cases: pinned files (the byte-level mirror of R15's row pins), locally processed inputs (a FASTA or MGF parsed in wasm needs bytes or ranges), and content this device authored but has not uploaded.

**Amended (R68, 2026-09-10):** browser HTTP uses worker `fetch` for the same request shapes as the native transport. Ticket URLs require HTTPS except for loopback HTTP, and redirects are refused. Local bytes become an `ObjectUrl` owned by a reference-counted handle, and the browser URL is revoked when its last owner drops. Remote resolution remains the signed server URL. The thirty second total deadline this amendment first named is replaced by the idle bound below.

**Decided (2026-09-14, before R69): a content transfer is bounded by silence, never by elapsed time.** One idle bound, thirty seconds by default, covers every phase of a request on both platforms: the transfer aborts when no byte has moved in either direction for that long, and a moving transfer is never aborted however long it runs. A valid chunk is 16 MiB and a download collects a whole file, so any total deadline is a floor on link speed that some link is below, and a transfer that fails it restarts from byte zero on every retry and never completes. The bound is one number because the silence after the last request byte, while the server verifies a chunk or runs the commit's whole verification, is the same silence to the client, so a deployment with a slow commit raises its bound rather than getting a second one. A deployment sets it through `DbWorkerConfig` in the browser and through the file client's own client builder natively, and a native application that passes its own `reqwest` client through `with_client` keeps that client's settings, since the point of that constructor is proxies and certificates the application already configured. What the bound does in every situation a transfer can be in:

| Event | Sending the body | Waiting for the status line | Receiving the body |
|---|---|---|---|
| Bytes move | Timer reset, except a browser `POST`, whose send shares the status wait's window | Not possible | Timer reset |
| Idle bound elapses | Abort, retryable | Abort, retryable | Abort, retryable |
| Status line arrives | Not possible | Timer reset, then receiving | Not possible |
| Body ends | Timer reset, then waiting | Not possible | Reply complete, timer cleared |
| Network failure | Retryable | Retryable | Retryable |
| Redirect, as a `3xx` reply or a reply landed on another origin than the ticket URL | Not possible | Refused, permanent | Refused, permanent |
| Local relay request | Served, transfer continues | Served, transfer continues | Served, transfer continues |

An abort is `Transport` and therefore retryable, because an unsent write cannot be refetched and a stalled link is exactly the ambiguous failure the outbox bias keeps. A reply from another origin is permanent under the two-event rule above, since it is an answer about the server, and the HTTPS or loopback validation of the ticket URL still runs first. How each platform observes the bytes: browser downloads read the response as a stream and reset the timer per received chunk, browser uploads run through `XMLHttpRequest`, the one portable source of upload progress in a worker, whose unconditional redirect following is why the origin of the landed reply is checked afterwards where `fetch` refused the redirect before. Native downloads use the client's read timeout as the idle bound and native uploads send the body as a stream that reports each write. Rejected: a deployment setting for the total deadline, which moves the wrong number from the source into configuration, and a deadline scaled from the body length by a minimum rate, which keeps a floor on link speed and needs the expected length of every download.

**Amended (2026-09-15, before R69): the browser sends the intent and the commit through `fetch`.** Only the chunk `PUT` moves to `XMLHttpRequest`, because only its body is large enough for the send to need observing. The intent body is the manifest, about a hundred bytes per chunk, and the commit carries no body, so a `POST` through `fetch` shares the download's streamed reply reader and its timer, which starts when the request leaves, is first reset by the status line and then by every received chunk. The silence before the status line covers the small body send and the server's wait as one window, which for a metadata sized body is the same silence. Rejected: `XMLHttpRequest` for every request with a body, which observes a send that never needs observing and gives up the redirect refusal `fetch` makes before a reply lands.

**Amended (2026-09-15, before R69): the native transport keeps its own watchdog and asks nothing of the `reqwest` client.** The read timeout the decision above named for native downloads is replaced. In `reqwest` 0.12 that setting restarts on every received frame of the reply, but on the request it is one sleep started at `send` and polled until the status line arrives, with no reset while the body goes out, so on a client that also uploads it is a total deadline on the send of a chunk, the floor on link speed the decision removed, and no per request setting switches it off. `ReqwestHttp` therefore carries the idle bound itself, thirty seconds by default and set through its own builder, and enforces it with one watchdog per request. The upload body goes out as a stream whose every pull is a write the connection accepted, the reply body is read as a stream whose every chunk is a receipt, both feed the same watchdog, and the request future is abandoned when the watchdog sees the bound of silence in any phase, including the wait for the status line. `new` builds a client with no timeout of any kind and `with_client` keeps the application's client untouched under the same watchdog, so a proxy or certificate the application configured reaches every request. An application client that set its own `read_timeout` or `timeout` still carries `reqwest`'s deadline on its uploads, which is that client's own setting and is stated at `with_client`. Rejected: a second client inside the transport for uploads, since `with_client` could then reach only one side. Rejected: the client's read timeout beside a stream idle for uploads, which aborts every moving upload slower than the chunk size over the bound.

**Amended (2026-09-15, before R69): a redirect is a refusal on every path, and it has one name.** The native transport's own client follows no redirect, the same rule browser `fetch` already keeps, because the mint issues exact URLs and no hop is part of the protocol. `reqwest` replays a `Vec` body to a redirect target and never a streamed one, and its redirect layer returns the reply of a `307` or `308` on an unreplayable body to the caller before the policy runs, so a policy that inspects the hop would never see the one on a chunk upload and a policy that follows would resend the intent manifest to a foreign origin before any check. With no following, every `3xx` reply reaches the negotiation on the ticket's own origin and is refused there beside the other status decisions. Two paths still land elsewhere, an application client passed through `with_client`, whose policy is its own, and `XMLHttpRequest`, and both check the origin of the landed reply against the ticket URL afterwards. Browser `fetch` asks for the `manual` redirect mode, whose opaque reply is distinguishable where the `error` mode's rejection is the same failure a dropped connection raises and was being retried. The refusal is `ContentError::Redirected` with the stage and the foreign origin when a landed reply revealed it, nothing when the redirect was refused before landing, and `outcome` classifies it `Refused`. The transport seam returns either its own failure or that refusal, and the origin comparison sits in the two transports that hold a landed URL, while the status rule sits above the seam. Rejected: a policy that follows same-origin hops, which adds a refusal source and still misses the streamed upload. Rejected: folding the refusal into the `Http` status variant, since the landed reply under `XMLHttpRequest` carries a success status and the `fetch` refusal carries none.

**Amended (2026-09-15, before R69): the ticket URL is validated once, above the transport seam, on both platforms.** A grant must be HTTPS, or HTTP on a loopback host, before any request leaves, natively as much as in the browser, because the ticket rides the URL query and a rewritten scheme would carry it in clear off the machine whatever the mint refused to sign. The rule runs where the grant's shape is already checked, beside the split of the write URL into its three addresses and at the entry of a download, with the parsed host rule the mint keeps rather than a text match, and a failing URL is `MalformedGrant`, an address that is not the shape the file server mints, permanent under the two-event rule. The browser transport no longer keeps its own copy, whose failure was a transport error and was being retried. Rejected: leaving native to the mint's refusal, which gives the two platforms different rules for one URL. Rejected: a copy of the rule in each transport with a third seam variant to carry the refusal, which is a decision the negotiation makes for both.

A file reference row is an intent. Metadata can arrive before content is fetchable, offline authorship makes that unavoidable rather than a bug, and readers show a placeholder until the availability signal below flips. Thumbnails are ordinary derived files behind a `thumb_hash` column, one pipeline with everything else.

## Server storage

**Decided (R24 position 4, R65).** Content bytes never enter Postgres. Beyond ordinary TOAST costs, this deployment runs `wal_level = logical`, so `BYTEA` content would be fully WAL-logged and pinned by the R32 replication slot, letting one bulk upload eat the retention headroom that keeps offline devices resumable. Chunks live in a filesystem directory or an S3-compatible object store behind the same `ChunkStore` trait. Manifests stay in Postgres through typed diesel. Chunk liveness is derived from manifest_chunks references and no counter is maintained. Garbage collection is mark-and-sweep: the sweep locks candidate registry rows, discards those still referenced by any manifest (committed or within the grace window equal to the upload ticket lifetime), and marks the rest deleting.

The backup story splits and the deployment documentation must say so: a database backup restores every metadata row and no bytes, so the chunk store needs its own durability statement. R70 owns the wider backup and restore story this feeds into.

## The wire, tickets, and the mint

**Decided (R24 positions 6 and 9, R66), with the capability distinction recorded in chapter 12.** An `img` tag cannot present a grant, so the URL itself must prove the right to fetch. A content ticket is a transport ticket carrying an already-made decision from the websocket to HTTP, deliberately not an R4 capability, which must never carry its own permission: the ticket is never presented at a handshake and never enters a `Principal`, and its revocation lag is exactly its lifetime, the same bounded staleness as the existing decision caching.

What rides the websocket is the ticket request (file id, verb, and for the write verb the declared byte size) and its grant. connetto calls a deployment-wired signer, the `WriteTarget` pattern. The signer, its key, the token format and the verifying HTTP endpoint all live in one file crate, so no key material and no token vocabulary enter `connetto-core` beyond the seam trait. The whole upload negotiation (intent, needed-hashes, chunk PUTs, commit) is HTTP under that ticket, and the file server enforces the ticket's byte ceiling rather than keeping a second counter. Tickets carry a session-long lifetime, accepting cross-session cache misses so a revocation cannot outlive the session that earned it.

**Amended (R66, 2026-09-08): the mint asks the same visibility function the serving check asks.** An earlier wording had connetto answer visibility "from the metadata row with its own machinery", which left open whether the mint and the serving path consult the same authority. They must, so connetto asks `connetto_visible_files` on the reader role, exactly as R65's dedup and serving checks do, and row level security and FGA decide the mint. Rejected: re-deriving the answer inside connetto from the application's own metadata row, which needs a file-id-to-row mapping connetto does not have and lets the mint and the serving check drift apart, so a file could be mintable and unservable or the reverse.

**Decided (R66, 2026-09-08): what a refused ticket request says.** An invisible file and an over-budget request answer one byte-identical `NonFatalError` detail, the way `SUBSCRIPTION_REFUSED` stays identical across causes, so a caller cannot learn that a file it cannot see exists. A signer failure answers a distinct detail, because it discloses nothing about any user's data and a retry is meaningful where retrying an invisibility is not. Rejected: reusing `RateLimited` for the over-budget case, because being over an upload budget is a refusal of the file that was named, and `retry_after_ms` would tell a caller the request would have succeeded later, which reopens the same oracle the identical detail closes.

The types a client builds against: `ContentTicketRequest` and `ContentTicketGrant` on `ControlMessage`, carrying `ContentVerb::Read` or `ContentVerb::Write { declared_len }` and a caller-chosen `request_id` echoed by the grant and by any refusal. The seam is `connetto_core::ContentTicketSigner`, implemented by `connetto_file_server::TicketSigner`, which holds the URL base, the ticket lifetime and the read ceiling, since a read carries no caller-declared size. Refusal details are `CONTENT_TICKET_REFUSED` and `CONTENT_TICKET_SIGNER_ERROR`.

**Amended (2026-09-12): the mint refuses a base that is not HTTPS or loopback.** `TicketSigner` validates `base_url` at construction time and returns `TicketError::InsecureBase` for any `http` base whose host is not `localhost`, `127.0.0.1`, or `[::1]`, so a misconfigured deployment fails at boot rather than minting interceptable grants per request.

## Upload, and the availability signal

**Decided (R24 position 5, R65).** Upload is two-phase: intent, the needed-hashes answer, chunk PUTs, and a commit that verifies dedup satisfaction, chunk hashes, the BLAKE3 identity, and that the committer is the manifest's original declarer, so a half-uploaded file is never a servable version and resume is re-sending the intent. Dedup satisfaction checks that every chunk is either stored through this upload or present in a committed manifest visible to the caller. That check runs as the reader role so RLS applies inside `connetto_visible_files`: a deployment whose function relies on RLS alone must have it run as a non-owner role, since the admin role owns the tables and bypasses RLS, which would silently accept invisible dedup targets. Committer identity is bound to the `uploaded_by` field written at intent time and refused with the same status as a failed visibility check so no new status distinction reopens the existence oracle. After commit the file server writes a `content_state` column on the metadata row and CDC delivers the flip to every subscribed device with the row's own policy gating who learns it: a convention, deliberately not a trait. That write needs a grant nothing provides by default, because the file server's role is not the row's owner and R1 forbids superuser and BYPASSRLS, so the deployment provisions a column-scoped UPDATE policy or a `SECURITY DEFINER` setter, verified at startup through the `preflight.rs` pattern.

## The abuse surface

**Decided (R24 position 7, R65).** The content channel's read ceiling caps one response and the write ceiling caps one upload, enforced against the ticket's ceiling, because R19 deliberately meters occurrences and file upload is the system's first genuinely bulk write path. Refusals answer 404 whether a file is absent or forbidden, R38's principle on HTTP. The dedup negotiation's needed-hashes answer is scoped to the caller's own visibility domain, closing the existence oracle cross-user dedup would open, while storage dedups globally and silently. Convergent encryption is rejected outright.

**Amended (R66, 2026-09-08): the upload direction gains windowed per-identity metering.** R65 left both directions unmetered across requests, so a caller bounded to 40 MB per upload could still mint a thousand tickets. connetto now charges a per-identity rolling bandwidth rate once at the mint, in `throttle.rs` beside the subscription, connection and credential limits. It stays in memory and adds no schema, because this is abuse prevention rather than accounting and a restart forgiving a few minutes of history is not an abuse vector. It charges the DECLARED size, so it caps authorized bandwidth and not measured bandwidth. Closing that gap would need the file server reporting actuals back to connetto, which R24 position 9 rejected as a second counter.

**Decided (R87, 2026-09-08): storage quotas and the deployment ceilings live in the file server.** A per-identity storage quota, a deployment-wide storage ceiling and a deployment-wide served-bandwidth ceiling, so an operator can say "we store at most 1 TB" or "we serve at most 1 TB a month". They belong here rather than in connetto because the numbers already do: `_cfs_manifests` carries `total_len` and `accepted_bytes` and `_cfs_manifest_chunks` carries `chunk_len`, so stored bytes are knowable per uploader and deployment-wide, measured rather than declared, at the moment a commit makes them true. This does not reopen position 9's rejection of a second counter, which concerned re-counting the ticket's bandwidth ceiling, a quantity connetto already knows. Storage is a quantity connetto cannot see at all. A ceiling refusal reaches the caller as the same byte-identical refusal and names the saturated ceiling only in the structured log, so an operator sees a ceiling filling instead of learning from a support ticket.

**Decided (R87, 2026-09-08): every declarer pays the full size.** Two callers uploading identical bytes each hold their own declaration, so each is charged the whole file and the deployment-wide ceiling is measured from real usage rather than by summing quotas. Per-user numbers therefore sum to more than the disk holds, which is intended: a user's usage never moves because a stranger uploaded or deleted the same content. Rejected: charging the deduplicated share, which makes one user's reported usage depend on what others store and is a weak cross-user signal about their content, and charging the first uploader only, which is unfair and leaves deletion owing someone else's bytes.

**Decided (R87, 2026-09-13): the ceilings are counted in Postgres over a rolling window, and a saturated request says which kind of full it is.** The file server scales out, so its served and accepted bytes are upserted into a per-day table every replica shares, the window is a trailing duration, and each replica checks a cached sum refreshed on a cadence with the overshoot bounded and stated. A commit over the uploader's own quota answers `507`, because the user can delete something. A deployment ceiling answers `503` with `Retry-After`, because nothing the user does helps and the outbox and the resolver already treat that answer as transient. This narrows the refusal rule above to its reason: no answer reveals existence or visibility, and a ceiling reveals neither. A warning fires once when usage crosses a configured fraction of any ceiling.
