## Purpose

Applications handle files: a photo attached to an entry, a dataset a scientist collected, a document. Rows are the wrong vehicle for their bytes, so file handling is its own subsystem: metadata travels as ordinary synced rows, content travels on its own channel with its own storage, and the boundary between the two is this chapter's subject.

## The boundary

**Decided (R24, concluded 2026-08-21).** connetto-core does not build file handling. The boundary is the crate, not the repository: the file crates live in this repository beside the demos, depend on connetto and never the reverse, and the demos carry the feature end to end per R54's rule. `connetto-core` deletes the old unimplemented `FileStore` trait and gains exactly one seam, the signer trait described under Tickets below (**Decided (R66)**).

The file crates own the traits with more than one implementation: `ChunkStore` (`write_chunk`, `read_chunk`, `has_chunk` and `delete_chunk` by content hash, with OPFS, `std::fs`, in-memory and object-store implementations), the application-facing content resolver, and the pin policy (**Decided (R64, R67)**).

**Amended (R67, 2026-09-08): `delete_chunk` joins the three original methods, and `ManifestStore` is not a trait.** The delete is what makes an unpin reclaim anything: without it a client that pinned a dataset once holds it forever, and the store is the only thing that can remove a chunk file. A store never decides that a chunk is unreferenced, because two manifests can name the same chunk, so that judgement stays with whoever holds the manifests. `ManifestStore` was named here as a trait and has exactly one implementation on each side of the wire, three typed tables in the replica on the client and three in Postgres on the server, so it is those tables rather than an abstraction over them. R79's peer source is the case that would have needed a second implementation, and it needs a content source rather than a manifest store.

**Amended (R67, 2026-09-09): `ChunkInventory` sits beside `ChunkStore`, and enumeration is deliberately not on it.** A store that can list what it holds implements the second trait, and the client's `std::fs` store, the in-memory store and R68's OPFS store all can. A deployment's object store is not asked to: it holds every file every caller ever uploaded, so answering "all of it" as one list is the wrong shape at that size, and the server sweeps from its chunk registry, the index it already keeps. This is the distinction the earlier rejection of a second storage trait turned on. Delete belongs on `ChunkStore` because a store that can be written and not pruned is a store whose disk only grows, and every store can prune. Enumeration is not universal in the same way, so a bound that demanded it of every store would be a bound the object store could only satisfy badly. Rejected: a fifth `ChunkStore` method, for that reason; and a durable staging record written before the chunk files, which cannot close the gap it exists for, because it would have to name hashes that only chunking produces.

## Identity, chunking, and the manifest

**Decided (R64).** A file's identity is the plain BLAKE3 hash of its bytes, computed in the same streaming pass as chunking. The identity is deliberately chunking-independent: BLAKE3 is internally a Merkle tree, so verified range streaming (bao) remains a later upgrade with no format change, anyone can recompute the identity with `b3sum`, and re-tuning chunk sizes never re-identifies a file. Rejected: a hash over the chunk hashes, whose identity silently depends on chunking parameters.

Content is split by FastCDC under a per-mime-class parameter table shipped as data, and a file at or under the maximum chunk size skips chunking. Compressed formats (JPEG, video, gzipped scientific data) get large parameters or whole-file treatment because sub-file dedup finds nothing in them. The manifest is the ordered list of per-chunk (BLAKE3, length) pairs, transport and dedup metadata only, lengths present because they map a byte range to chunks.

Each chunk is zstd-compressed (level 3, per-mime skip table, a compression flag in the chunk header) between chunking and encryption, the Borg and Kopia order: the dedup hash is always over plaintext. Text-heavy scientific data roughly halves under zstd, and the driving use case is exactly that.

## Client storage

**Decided (R24 position 3, R64, R67, R68).** One encrypted chunk store outside SQLite: chunk files in OPFS in the browser and plain files on native, each encrypted with XChaCha20-Poly1305 under a random 24-byte nonce stored with the ciphertext, the chunk's plaintext hash as authenticated associated data, and the key derived by BLAKE3 key derivation with a purpose label (decided 2026-09-02, superseding the HKDF wording: one hash family, zero extra dependencies) from the same custody `ReplicaKeyStore` serves, so the R23 unlock gate and crypto-shred-on-wipe cover content exactly as they cover the replica. XChaCha was chosen over AES-GCM at review: the 192-bit nonce removes the birthday bound and the AES-NI assumption on mobile cores, and the cipher is one shared pure-Rust layer on every target where the replica cipher is two (SQLCipher native, sqlite3mc wasm).

**Amended (R67, 2026-09-08): the manifests and the upload outbox live in the replica, not in the device-private tier.** They are committed in the same transaction as the entry row, so a crash orphans a chunk file (collected by sweep) but never commits a row pointing at bytes that were never written. SQLite never carries content bytes on either side of the wire.

The tier cannot hold them, because the invariant and the tier are incompatible and the incompatibility is silent. The replica is opened `PRAGMA journal_mode=WAL` before the tier is attached, so the two are separate files and SQLite's atomic commit spans attached databases only while no database in the set is WAL. Measured: a transaction writing both files commits with no error, and a host crash inside that commit may update one file and not the other. Manifests carry the `_connetto_` prefix that already marks connetto's own bookkeeping in the replica, beside `_connetto_meta`, `_connetto_pending` and the subscription set, which keeps them out of capture, out of the tier's application-table listing and off the wire. This is R20's correction applied to the same problem, and it carries R20's second reason too: the tier is optional and defaults to absent, so a tier-resident manifest would make file handling unavailable to any client that did not ask for one. It also gives R68 its archive step for free, since the R26/R56 archive exports the replica. Rejected: keeping them in the tier and dropping the invariant for a sweep of manifests with no row, because the reverse case is unrecoverable, a row naming a `file_id` whose chunk files are all present but whose chunk list and order are gone, which is the production failure the invariant exists to prevent, merely rarer. Rejected: putting the tier in WAL as well, which loses cross-file atomicity for exactly the same reason.

Client content divides into two classes. Unsent content, authored here and not yet uploaded, is data: its chunk files travel in the R26/R56 archive by manifest walk, because an unsent write cannot be refetched. Fetched content is cache: evictable under pin rules, never exported, refetchable by construction. The rejected alternatives (all chunks as encrypted-tier blobs, all chunks in plaintext OPFS, and a provenance split routing unsent bulk into SQLite) are recorded in the plan's R24 section.

## Display is not sync

**Decided (R24 position 2).** The common case renders a short-lived signed URL and never touches client chunk storage: the file server assembles from chunks and serves plain HTTP with `Range` mapped through the manifest, a strong `ETag` equal to the content hash, and immutable caching, so the browser's own cache, progressive rendering and video seeking do their jobs. Local content sync happens in exactly three cases: pinned files (the byte-level mirror of R15's row pins), locally processed inputs (a FASTA or MGF parsed in wasm needs bytes or ranges), and content this device authored but has not uploaded.

A file reference row is an intent. Metadata can arrive before content is fetchable, offline authorship makes that unavoidable rather than a bug, and readers show a placeholder until the availability signal below flips. Thumbnails are ordinary derived files behind a `thumb_hash` column, one pipeline with everything else.

## Server storage

**Decided (R24 position 4, R65).** Content bytes never enter Postgres. Beyond ordinary TOAST costs, this deployment runs `wal_level = logical`, so `BYTEA` content would be fully WAL-logged and pinned by the R32 replication slot, letting one bulk upload eat the retention headroom that keeps offline devices resumable. Chunks live in a filesystem directory or an S3-compatible object store behind the same `ChunkStore` trait. Manifests stay in Postgres through typed diesel. Chunk liveness is derived from manifest_chunks references and no counter is maintained. Garbage collection is mark-and-sweep: the sweep locks candidate registry rows, discards those still referenced by any manifest (committed or within the grace window equal to the upload ticket lifetime), and marks the rest deleting.

The backup story splits and the deployment documentation must say so: a database backup restores every metadata row and no bytes, so the chunk store needs its own durability statement. R70 owns the wider backup and restore story this feeds into.

## The wire, tickets, and the mint

**Decided (R24 positions 6 and 9, R66), with the capability distinction recorded in chapter 12.** An `img` tag cannot present a grant, so the URL itself must prove the right to fetch. A content ticket is a transport ticket carrying an already-made decision from the websocket to HTTP, deliberately not an R4 capability, which must never carry its own permission: the ticket is never presented at a handshake and never enters a `Principal`, and its revocation lag is exactly its lifetime, the same bounded staleness as the existing decision caching.

What rides the websocket is the ticket request (file id, verb, and for the write verb the declared byte size) and its grant. connetto calls a deployment-wired signer, the `WriteTarget` pattern. The signer, its key, the token format and the verifying HTTP endpoint all live in one file crate, so no key material and no token vocabulary enter `connetto-core` beyond the seam trait. The whole upload negotiation (intent, needed-hashes, chunk PUTs, commit) is HTTP under that ticket, and the file server enforces the ticket's byte ceiling rather than keeping a second counter. Tickets carry a session-long lifetime, accepting cross-session cache misses so a revocation cannot outlive the session that earned it.

**Amended (R66, 2026-09-08): the mint asks the same visibility function the serving check asks.** An earlier wording had connetto answer visibility "from the metadata row with its own machinery", which left open whether the mint and the serving path consult the same authority. They must, so connetto asks `connetto_visible_files` on the reader role, exactly as R65's dedup and serving checks do, and row level security and FGA decide the mint. Rejected: re-deriving the answer inside connetto from the application's own metadata row, which needs a file-id-to-row mapping connetto does not have and lets the mint and the serving check drift apart, so a file could be mintable and unservable or the reverse.

**Decided (R66, 2026-09-08): what a refused ticket request says.** An invisible file and an over-budget request answer one byte-identical `NonFatalError` detail, the way `SUBSCRIPTION_REFUSED` stays identical across causes, so a caller cannot learn that a file it cannot see exists. A signer failure answers a distinct detail, because it discloses nothing about any user's data and a retry is meaningful where retrying an invisibility is not. Rejected: reusing `RateLimited` for the over-budget case, because being over an upload budget is a refusal of the file that was named, and `retry_after_ms` would tell a caller the request would have succeeded later, which reopens the same oracle the identical detail closes.

The types a client builds against: `ContentTicketRequest` and `ContentTicketGrant` on `ControlMessage`, carrying `ContentVerb::Read` or `ContentVerb::Write { declared_len }` and a caller-chosen `request_id` echoed by the grant and by any refusal. The seam is `connetto_core::ContentTicketSigner`, implemented by `connetto_file_server::TicketSigner`, which holds the URL base, the ticket lifetime and the read ceiling, since a read carries no caller-declared size. Refusal details are `CONTENT_TICKET_REFUSED` and `CONTENT_TICKET_SIGNER_ERROR`.

## Upload, and the availability signal

**Decided (R24 position 5, R65).** Upload is two-phase: intent, the needed-hashes answer, chunk PUTs, and a commit that verifies dedup satisfaction, chunk hashes, the BLAKE3 identity, and that the committer is the manifest's original declarer, so a half-uploaded file is never a servable version and resume is re-sending the intent. Dedup satisfaction checks that every chunk is either stored through this upload or present in a committed manifest visible to the caller. That check runs as the reader role so RLS applies inside `connetto_visible_files`: a deployment whose function relies on RLS alone must have it run as a non-owner role, since the admin role owns the tables and bypasses RLS, which would silently accept invisible dedup targets. Committer identity is bound to the `uploaded_by` field written at intent time and refused with the same status as a failed visibility check so no new status distinction reopens the existence oracle. After commit the file server writes a `content_state` column on the metadata row and CDC delivers the flip to every subscribed device with the row's own policy gating who learns it: a convention, deliberately not a trait. That write needs a grant nothing provides by default, because the file server's role is not the row's owner and R1 forbids superuser and BYPASSRLS, so the deployment provisions a column-scoped UPDATE policy or a `SECURITY DEFINER` setter, verified at startup through the `preflight.rs` pattern.

## The abuse surface

**Decided (R24 position 7, R65).** The content channel's read ceiling caps one response and the write ceiling caps one upload, enforced against the ticket's ceiling, because R19 deliberately meters occurrences and file upload is the system's first genuinely bulk write path. Refusals answer 404 whether a file is absent or forbidden, R38's principle on HTTP. The dedup negotiation's needed-hashes answer is scoped to the caller's own visibility domain, closing the existence oracle cross-user dedup would open, while storage dedups globally and silently. Convergent encryption is rejected outright.

**Amended (R66, 2026-09-08): the upload direction gains windowed per-identity metering.** R65 left both directions unmetered across requests, so a caller bounded to 40 MB per upload could still mint a thousand tickets. connetto now charges a per-identity rolling bandwidth rate once at the mint, in `throttle.rs` beside the subscription, connection and credential limits. It stays in memory and adds no schema, because this is abuse prevention rather than accounting and a restart forgiving a few minutes of history is not an abuse vector. It charges the DECLARED size, so it caps authorized bandwidth and not measured bandwidth. Closing that gap would need the file server reporting actuals back to connetto, which R24 position 9 rejected as a second counter.

**Decided (R87, 2026-09-08): storage quotas and the deployment ceilings live in the file server.** A per-identity storage quota, a deployment-wide storage ceiling and a deployment-wide served-bandwidth ceiling, so an operator can say "we store at most 1 TB" or "we serve at most 1 TB a month". They belong here rather than in connetto because the numbers already do: `_cfs_manifests` carries `total_len` and `accepted_bytes` and `_cfs_manifest_chunks` carries `chunk_len`, so stored bytes are knowable per uploader and deployment-wide, measured rather than declared, at the moment a commit makes them true. This does not reopen position 9's rejection of a second counter, which concerned re-counting the ticket's bandwidth ceiling, a quantity connetto already knows. Storage is a quantity connetto cannot see at all. A ceiling refusal reaches the caller as the same byte-identical refusal and names the saturated ceiling only in the structured log, so an operator sees a ceiling filling instead of learning from a support ticket.

**Decided (R87, 2026-09-08): every declarer pays the full size.** Two callers uploading identical bytes each hold their own declaration, so each is charged the whole file and the deployment-wide ceiling is measured from real usage rather than by summing quotas. Per-user numbers therefore sum to more than the disk holds, which is intended: a user's usage never moves because a stranger uploaded or deleted the same content. Rejected: charging the deduplicated share, which makes one user's reported usage depend on what others store and is a weak cross-user signal about their content, and charging the first uploader only, which is unfair and leaves deletion owing someone else's bytes.
